# Executor Code Style

本规范适用于 `autowsgr/business/**/executor.py`，也作为其他业务执行器的默认排版约定。
它只统一代码组织方式，不要求不同业务共享相同的状态字段或返回值。

## 文件顺序

```text
模块说明
标准库导入
项目导入
TYPE_CHECKING
日志器和模块常量
执行器类
```

执行器类内按下面顺序组织。没有对应内容的分组直接省略。

```python
class XxxExecutor(BaseExecutor):
    """一句话说明执行边界。"""

    # ── 初始化 ─────────────────────────────────────────────────
    def __init__(...):
        ...

    # ── 主流程 ─────────────────────────────────────────────────
    def _execute(...):
        ...

    # ── 单次业务动作 ───────────────────────────────────────────
    def _run_one(...):
        ...

    # ── 进度与断点 ─────────────────────────────────────────────
    def _save_progress(...):
        ...

    # ── 业务辅助 ───────────────────────────────────────────────
    def _has_quota(...):
        ...


```

## 主流程要求

`_execute()` 从上到下应能对应实际业务链路：读取进度、初始化或恢复、导航、准备、执行、
保存结果、返回。每一个实际业务步骤都必须在对应代码前写一条短注释，步骤编号按执行顺序递增。
业务差异写在流程内容里，不通过大量模式开关隐藏。

只有满足下面任一条件时才拆出新的 `def`：

- 同一段逻辑被调用两次以上；
- 具备独立业务含义或副作用边界；
- 需要独立测试；
- 回调协议或进度保存必须有明确入口。

单行转发、只调用一次且没有独立语义的代码直接留在主流程中。执行器不实现页面点击、OCR
细节或设备操作，这些放在同域 `operations.py` 或下层 application/common。

## 注释与文档字符串

- 模块 docstring 说明执行范围、次数语义和特殊恢复规则，使用短句；
- 类 docstring 只说明执行器负责什么、不负责什么；
- 主流程使用 `# 1、...` 这类短注释标出每一个真实业务阶段；
- 初始化、导航、页面准备、业务执行、结果保存、断点和清理都必须有对应注释；
- 注释放在该步骤第一条语句前，说明“要做什么”和必要的业务原因；
- 一个步骤一条注释即可，不为赋值、条件或函数调用逐行写旁白；
- 分组使用统一的 `# ── 名称 ──` 横线注释，分组名使用中文；
- 注释解释业务原因、边界或恢复语义，不逐行复述代码；
- 不连续堆叠空行，不使用长篇设计说明代替代码结构。

## 日志与测试

- 新链路日志统一为 `[EnglishModule] 中文消息`；
- 日志模块名按职责固定，例如 `[Campaign]`、`[Exercise]`、`[Fleet]`、`[OCR]`；
- 新增分支至少保留一个能失败的专项测试；纯一行转发不新增测试；
- 修改执行器后只运行对应业务专项测试，完整测试在切片验收时运行。

## 迁移规则

执行器不在业务模块导入时自注册。`autowsgr.dispatch.registry` 维护
`task_type -> (模块, 类名)` 的显式映射，并按需加载执行器。

本规范从 2026-09-03 起用于新增和实际修改的执行器。旧兼容代码不因排版规范单独批量重写，
避免把格式整理和行为迁移混在一个提交中。
