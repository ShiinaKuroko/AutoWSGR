# UI 模块级规范

## 0. 规则继承与覆盖

本规范继承 `docs/features/[规范]python-code-style.md` 的全部通用 Python 规则。

本规范只补充：

- 页面模块的文件职责；
- `page.py` 的公开入口和内部实现边界；
- 导航器、业务层、状态机和上下文的调用关系；
- 导航器与页面控制器之间的调用契约（含点击落点）；
- `recognition.py`、`operations.py`、`workflow.py` 的依赖方向。

除非本文件明确写出“覆盖 Python 规范第 X 条”，否则 Python 全局规范继续生效。
模块专项规范可以收紧全局规则，但不得在没有明确标记的情况下改写全局规则。
同一优先级的规范出现冲突时，Agent 必须暂停实现并报告冲突。

Agent 执行时应按这个顺序判断：

~~~text
用户要求 / AGENTS.md
        ↓
模块专项规范
        ↓
Python 全局规范
        ↓
代码现状和测试
~~~

具体到 page 调用关系：

~~~text
业务层 ──业务参数──→ page 完整业务流程 ──结果/异常──→ 业务层

导航器 ──导航契约──→ page 页面检查/返回

状态机、上下文 ──只接收──→ page 返回的结果、状态、事件

page 内部：
page → 私有 operation / recognition → common
~~~

本规范是 UI 模块的专项规则，适用于 application/ui 下的导航器与页面控制器。
通用 Python 文件骨架、import、常量、函数命名、注释、docstring 和基础验证，
统一以 docs/features/[规范]python-code-style.md 为准；本文件只定义页面模块的职责、
规模扩展和依赖边界，不重复通用规则。

本规范约束导航器与页面控制器的代码和相互调用，不替代 `navigation.md` 的设计说明、
业务任务、运行时上下文或 common 层自身的规范。页面模块的公共入口必须稳定，
具体业务契约仍以实现和测试为准。

## 1. 页面模块基线

页面型模块使用具有业务语义的 xx_page/ 目录。默认结构如下：

~~~text
xx_page/
├── __init__.py
├── page.py
├── recognition.py
└── constants.py
~~~

这个结构表达三类固定职责：

- page.py：作为页面包的对外流程门面，只提供导航契约和完整页面业务流程入口，接收业务参数，
  编排内部页面操作并返回结果或明确异常。
- recognition.py：仅在下层能力是“从外部输入读取或转换页面事实”时使用；
  它可以调用 common 提供的基础能力，不限定为 OCR、ROI 或 Vision，默认不作为包外 API。
- constants.py：负责当前模块范围内共享的页面业务校准数据，尤其是坐标、颜色、
  ROI 和其他静态屏幕参数。
- __init__.py：只导出稳定的页面入口和确实需要公开的数据类型。

对于视觉页面，通常仍使用 page.py、recognition.py、constants.py 三个文件。
如果下层文件实际负责的不是事实识别，而是其他独立能力，则必须按真实语义命名，
例如 data.py、state.py、policy.py 或 adapter.py；不得为了凑结构继续称为
recognition.py。三类职责保持不变，文件名不强行固定。

每个文件都必须有真实职责。非页面模块不套用页面模板，也不得创建空文件来凑目录结构。

## 2. 按规模扩展

文件数量不是目标，职责边界才是目标。只有当一组代码拥有独立的依赖、测试边界、
复用对象、状态所有权或变化节奏时，才新增文件。代码行数只能作为发现问题的信号，
不能作为机械阈值。

### 2.1 小型页面模块

小型页面只保持三类基线职责：

~~~text
page.py
recognition.py 或其他语义明确的下层能力模块
constants.py
~~~

页面流程不长、没有可复用独立操作时，页面原子操作和状态读取保留在 page.py 的私有实现中，
对外只暴露导航契约和完整页面业务流程入口。不要为了形式新增 operations.py 或 workflow.py。

### 2.2 中型页面模块

当页面操作或流程形成清晰的独立职责时，按语义增加文件：

~~~text
xx_page/
├── __init__.py
├── page.py
├── recognition.py 或其他下层能力模块
├── constants.py
├── operations.py   # 有独立页面基础操作集合时
└── workflow.py     # 有独立多步骤子流程时
~~~

operations.py 和 workflow.py 可以同时存在，但两者职责不得重叠。

operations.py 负责页面包内部可复用的基础操作：

- 一个明确页面意图对应一个操作；
- 可以执行点击、选择、滑动、打开、关闭和直接终态确认；
- 可以使用设备控制器、common.ui.interaction 和 constants.py；
- 不负责复杂分页、候选决策、重试分支或最终业务结果；
- 不反向依赖 page.py 的实现细节。

operations.py 的函数只服务于 page.py 或 workflow.py，不作为页面包的公开入口。

workflow.py 负责可复用的多步骤业务子流程：

- 组合页面操作和下层事实读取；
- 负责分页、候选选择、条件分支、有限重试和结果判断；
- 对上层隐藏流程内部步骤；
- 使用业务动词命名，例如 repair_ship、repair_longest；
- 不得变成无法用一句话说明职责的“其他代码”文件。

workflow.py 的流程必须拥有独立的业务契约或真实复用者，不得只是把 page.py 的公开入口
拆成另一个文件；它的内部步骤同样不作为页面包公开 API。

page.py 仍是上层入口和页面级总编排者。它可以调用 workflow.py，但不得与
workflow.py 重复实现同一个完整流程。只有实际存在独立流程边界时才拆分。

### 2.3 大型页面模块

大型模块按独立业务能力拆成子包，而不是继续向单个目录添加模糊文件：

~~~text
domain/
├── main_page/
├── feature_a/
├── feature_b/
└── support/
    ├── feature_c/
    └── feature_d/
~~~

拆成子包的条件是该能力拥有独立的输入、结果、状态所有权、流程边界或测试边界。
页面型子包可以使用本规范的页面基线；非页面流程包只创建实际需要的语义文件，
不强行创建 recognition.py 或 constants.py。

大型模块继续拆分前，必须能回答：

1. 新子包负责哪个单一业务能力；
2. 输入、输出和可观察终态是什么；
3. 谁拥有其中的可写状态；
4. 父流程为什么能把它作为一个独立节点调用；
5. 它的测试和依赖边界是否独立。

## 3. 文件职责

### 3.1 page.py

page.py 定义页面控制器，是页面模块对上层的稳定入口，负责：

- 组织页面级流程和状态转换；
- 只暴露导航器需要的页面导航契约和业务层需要的完整业务流程入口；
- 接收并校验业务参数，编排私有页面操作和下层能力；
- 组合 operations.py、workflow.py 和下层能力模块；
- 确认页面、浮层或业务动作的成功终态，并返回上层需要的结果。

page.py 不负责：

- 实现 OCR、文本解析、图像检测或其他下层算法；
- 复制坐标、颜色、ROI 或下层 common 的实现；
- 跨任务调度、用户配置持久化或创建运行时上下文；
- 和 workflow.py 重复实现相同的完整子流程。

小型页面尚未形成 operations.py 时，可以保留少量页面专用原子动作。形成独立
operations.py 后，page.py 不得绕过它复制同一组设备操作。

page.py 不得因为某个中间操作可被调用或便于测试，就把它提升为公开方法。外部调用方
只能传入业务参数并调用完整入口，不能依赖 close_*、select_* 或其他中间步骤自行拼装流程。

### 3.2 recognition.py 和下层能力模块

recognition.py 的名称只适用于其主要职责是读取或转换页面事实，例如：

- 从截图、OCR、像素或模板读取页面状态；
- 将外部输入转换为页面事实或结构化结果；
- 执行识别所需的标准化、解析和结果组合。

它可以调用 common 中与该职责对应的基础能力，但不限定为 OCR、ROI 或 Vision。
如果模块主要负责其他下层能力，则使用与结果相符的名称：

- data.py：读取或组合模块专属静态数据；
- state.py：读取或转换运行状态；
- policy.py：执行纯规则判断或目标选择；
- adapter.py：适配明确的外部接口；
- 其他名称：只有职责和所有权足够明确时才允许使用。

这些下层能力模块共同遵守：

- 只向下依赖基础设施、common 和当前模块的 constants.py；
- 不导入 page.py、workflow.py 或上层业务模块；
- 不持有页面流程状态，不决定跨页面导航或任务调度；
- 不创建第二套上下文、缓存或状态所有者；
- 输入、输出和失败边界必须通过函数签名、结果类型或明确异常表达。

如果文件实际只有视觉事实读取，保持 recognition.py。换成其他文件名必须同时更新
__init__.py、导入方、调用方、测试、注释和文档，不保留没有真实消费者的旧别名。

### 3.3 constants.py

constants.py 负责当前页面模块的共享静态校准数据：

- 页面和控件的点击坐标；
- 滑动起点、终点和动作参数；
- 页面专用的 OCR 坐标和 ROI；
- 颜色、尺寸、阈值和模板校准值；
- 多个模块文件共同消费的页面静态数据。

坐标、ROI、颜色和模板参数必须按页面业务区域分组，遵循通用 Python 规范中的
命名、单位、精度和注释规则。一个值只能有一个定义源。

流程专属的超时、最大尝试次数、分页上限和重试策略留在 page.py 或 workflow.py。
只被某个下层算法消费的阈值留在该算法文件。不得为了集中配置把所有值搬进
constants.py。

constants.py 不得保存 GameContext、设备对象、OCR 引擎、可变运行时状态、调度规则、
其他页面坐标或没有真实消费者的预留映射。

### 3.4 operations.py

operations.py 是可选的页面基础操作层。它适合承载多个流程需要复用、但仍属于
当前页面的操作：

- 打开或关闭页面内浮层；
- 点击明确的页面对象；
- 滑动列表；
- 选择页面选项；
- 执行一个操作并确认直接页面终态。

operations.py 中的 click_* 只能表示原子点击。包含查找、分页、重试、候选选择和
最终结果判断的代码必须使用业务动词，放到 page.py 或 workflow.py。

operations.py 不得成为暂时无法归类代码的收容文件，也不得通过反向导入 page.py
隐藏依赖方向。

### 3.5 workflow.py

workflow.py 是可选的页面子流程层。它适合承载：

- 多个页面操作的固定组合；
- 跨多个 UI 状态的完整业务动作；
- 需要分支、循环、重试、候选选择或失败终态的流程；
- 父页面能够作为一个独立节点调用的流程。

workflow.py 可以依赖 operations.py、下层能力模块、constants.py 和 common 的
设备/等待基础设施，但不得创建第二套上下文或状态源。它的函数必须使用业务语义
命名，不能用 process、do、manage 或 other 等宽泛词汇。

## 4. 依赖方向

页面包的允许调用关系与内部依赖方向分开描述：

~~~text
导航器       ──调用页面检查/返回契约──────→ page.py
业务层       ──传入业务参数调用完整流程──→ page.py
状态机/上下文 ←──接收 page 返回的结果/状态/事件── page.py
~~~

业务层不参与页面内部步骤，导航器不负责业务流程编排；状态机和上下文不反向调用页面。

页面模块内部保持单向依赖：

~~~text
__init__.py
      ↓
page.py
  ↓     ↓       ↓
workflow  operations  下层能力模块
   ↓        ↓              ↓
   └────────┴──────→ constants.py
                         ↓
              common / device / vision / data
~~~

实际规则如下：

- 包外生产代码只从页面包的公开入口导入；
- page.py 负责流程编排，但不复制下层实现；
- workflow.py 可以组合 operations 和下层能力模块；
- operations.py 只依赖页面校准和设备/交互基础设施；
- recognition.py 或其他下层能力模块只向下依赖适配的 common 能力；
- constants.py 不依赖页面、流程、设备或识别实现；
- 下层模块不得反向导入 page.py 或上层业务模块；
- 任何新增跨层依赖都必须能在 Code Graph 中解释方向和所有权。

common 不是单一职责：

- 视觉、OCR、像素和图像处理通常归 recognition.py；
- 其他基础 common 能力归与其语义匹配的下层能力模块；
- 设备点击、滑动、等待和导航基础设施归 operations.py 或 workflow.py；
- page.py 只消费稳定契约，不复制 common 的实现。

如果同一模块的下层能力从视觉识别变成其他能力，文件名和职责说明必须一起调整。
不能让 recognition.py 继续作为无意义的通用下层入口。

## 5. 公共入口与状态所有权

每个页面包必须通过 __init__.py 提供稳定入口：

- 页面控制器通常由 page.py 定义并由包入口导出；
- 识别结果或其他下层结果类型只有在确实是上层契约时才导出；
- operations.py、workflow.py 和下层能力模块的内部函数默认不作为包外 API；
- 不使用包级动态属性、导入别名或复制实现伪造兼容入口；
- 包外模块不得依赖私有方法、私有常量或深层实现路径。

### 5.1 页面公开入口

页面包的公开方法必须同时满足以下条件：

- 存在真实且被架构允许的上层或同层调用方；
- 表达一个完整的页面意图、导航契约或页面业务流程；
- 由页面方法负责参数校验、内部编排、成功终态和失败异常；
- 不要求调用方了解页面内部步骤、识别细节或操作顺序。

导航器是页面模块唯一允许的同层直接调用者，只能调用页面检查、页面返回和导航相关契约。
业务层只依赖页面公开的完整业务流程，通过业务参数获得页面或业务结果及明确异常，不依赖
页面原子操作、识别细节或内部步骤。其他 application 同层模块不得直接调用页面；状态机和
上下文只收集页面返回的结果、状态或事件。测试和 E2E 的直接调用不能单独构成公开入口。

页面控制器只保存调用方注入的上下文。页面模块内部的可写状态必须有单一所有者，
并明确创建、更新和销毁边界。结果和失败原因优先使用结构化类型或明确异常，
不通过旁路属性或多个互相覆盖的标志传递状态。

页面动作必须说明成功终态。点击成功不等于业务成功；需要确认页面、浮层或业务结果
时，必须由 page.py 或 workflow.py 完成确认。

### 5.2 导航器与页面控制器的点击契约

页面点击的落点由导航器按识别结果传入，控制器决定是否兜底：

| 页面类型 | 导航器调用时 | 控制器行为 |
| --- | --- | --- |
| 活动页控制器 | 不传中心坐标 | 自己取识别中心；识别失败即失败，不设静态兜底 |
| 其他页面控制器（有模板） | 传 `TemplateMatchResult.center` | 用传入的中心；中心为空时按静态坐标兜底 |
| 无模板的页面 | 不传 | 直接按静态坐标点击 |

- 中心坐标的源头是 page_checker 的 `read_*_center` 入口，取值来自
  `TemplateMatchResult.center`（命中模板的归一化中心）；
- 静态坐标和兜底位置属于 `constants.py` 的校准数据；
- 控制器不得为了补中心自行截图或重新识别，落点参数由导航器统一提供。

## 6. 页面模块内的编排顺序

通用文件顺序、空行、import、注释和 docstring 规则见 Python 规范。本规范只补充
页面语义。

page.py 通常按以下阅读顺序排列：

1. __init__；
2. 页面级主流程和允许调用方使用的公开入口；
3. check_*、read_* 等页面事实入口；
4. open_*、close_*、select_* 和 click_* 等页面节点；
5. 组合业务流程；
6. go_back、navigate_to 等页面级边动作；
7. 私有页面操作和私有辅助方法。

上述顺序只表示 page.py 的内部阅读顺序，不等同于公开 API 清单。check_*、read_*、
open_*、close_* 和 select_* 等分类中的方法，只有满足第 5.1 节的真实调用者和完整契约
时才允许公开；其他方法必须作为页面内部实现。

下层能力模块按其真实职责排列：

- recognition.py：模型 → 标准化/解析 → 事实识别 → 结果组合；
- data.py：数据加载 → 标准化 → 数据查询；
- state.py：状态读取 → 状态转换 → 状态结果；
- policy.py：输入规则 → 纯判断 → 选择结果；
- adapter.py：外部输入 → 契约转换 → 明确结果。

operations.py 按页面实际操作顺序排列；workflow.py 按完整流程节点排列。禁止按
字母顺序排列所有函数，也禁止使用“其他”“辅助”“工具函数”等没有业务含义的
分区标题。

## 7. 命名规则

通用函数前缀和业务语义规则见 Python 规范。本规范的页面补充如下：

- page.py 的顶层流程使用真实业务动词；
- recognition.py 使用 recognize_*、read_*、parse_*、normalize_* 等事实转换语义；
- operations.py 使用 open_*、close_*、click_*、select_*、wait_* 等页面操作语义；
- workflow.py 使用业务流程动词，不使用 click_* 包装复杂流程；
- check_* 只检查状态，不产生副作用；
- wait_* 必须写明等待的页面或业务终态；
- 不用 process、do、manage、handle_data、core、other 等宽泛名称。

page.py、recognition.py、constants.py、operations.py 和 workflow.py 只有在父目录
已经提供完整业务上下文时才使用。下层能力如果不是识别，必须改成与其职责匹配的
文件名。禁止用 core.py、base.py、utils.py、helpers.py、misc.py 或 common.py
规避职责命名。

## 8. 规模样例

规模扩展遵循以下顺序：

~~~text
固定三类职责
  → 形成独立页面基础操作时增加 operations.py
  → 形成独立多步骤流程时增加 workflow.py
  → 出现多个业务能力时拆成语义明确的子包
~~~

Fleet 可作为大型模块的参考，但不是目录模板。它按出征准备页、编队、选船、维修、
补给等业务能力划分 main_page、formation 和 support；每个 workflow.py 只负责自己
的业务流程，recognition.py 只在确实读取事实时使用，models.py 只在有独立数据契约
时出现。

页面模块变大时，应先判断是新增 operations、workflow，还是拆出新的业务子包，
不能把所有新增内容塞入一个“剩余模块”。

对于 bath_page：

~~~text
bath_page/
├── __init__.py
├── page.py          # 流程编排和上层入口
├── recognition.py   # 仅在下层职责是事实识别时保留
└── constants.py     # 浴室页面坐标和校准
~~~

如果浴室页面出现可复用的页面操作，增加 operations.py；如果出现独立的多步骤
修理流程，增加 workflow.py。若新增下层能力不是事实识别，则按真实职责改名，
不要保留 recognition.py 作为万能文件。

## 9. 注释、文档和验证

模块级 docstring 只说明职责、上层入口、下层能力和关键边界；通用长度和 Google
风格要求见 Python 规范。不要在每个文件中手工维护完整调用方清单，稳定的依赖事实
由 Code Graph 和真实导入提供。

每次页面模块结构调整至少验证：

- 页面包公开入口可以导入；
- 包外调用方只依赖页面包公开入口，不直接拼装页面内部步骤；
- 目标模块和直接调用方通过编译或 import smoke；
- page.py 负责流程编排，未复制下层算法；
- recognition.py 或其他下层能力模块没有反向依赖 page.py；
- constants.py 没有运行时状态或重复配置；
- operations.py 不承担完整业务流程；
- workflow.py 的输入、结果和失败终态明确；
- 结构或依赖变化时执行 Code Graph 的 explain、check 或 diff；
- 执行 git diff --check。

涉及真实设备的页面行为，仍需按风险决定模拟器或实机验证；静态检查和编译成功不能
替代页面终态、下层结果和真实导航行为验证。

## 10. 明确禁止

- 不把“除了三个文件以外的内容”收容到一个没有单一职责的模块；
- 不为凑结构创建空的 recognition.py、constants.py、operations.py 或 workflow.py；
- 不把 recognition.py 固定解释为 OCR、ROI 或 Vision；文件名必须匹配真实下层职责；
- 不默认增加 action.py；除非形成独立、稳定且不与 operations.py 重复的语义边界；
- 不让 page.py、operations.py 和 workflow.py 重复实现同一流程；
- 不让下层能力模块点击设备、决定跨页面导航或修改上层业务状态；
- 不把页面坐标、ROI、颜色和校准参数复制到 common 或多个页面；
- 不把页面原子操作、识别细节或状态读取细节作为包外流程 API；
- 不通过包级导出、导入别名或兼容包装隐藏真实所有权；
- 不因为模块规模变大就顺带重构无关页面、重命名全仓目录或清理无关测试；
- 不用注释、静默 fallback 或第二套状态源掩盖真实依赖方向和失败终态。
