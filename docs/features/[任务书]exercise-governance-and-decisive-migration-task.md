## 二、分层治理边界

### `business`

- `ExerciseSpec`、`CampaignSpec`：任务字段校验和业务规则。
- `ExerciseExecutor`、`CampaignExecutor`：任务循环、次数、暂停恢复和业务结果。
- 演习对手选择、战役难度/章节、战役固定槽位等业务决策。
- `[Exercise]`、`[Campaign]` 语义日志。

### `application`

- 共享 `Navigator` 和页面语义操作。
- `BattlePreparationPage`、补给、快速维修、船损识别。
- 通用舰队规则模型、选船入口和按 `task_type` 分支的编队能力。
- 战斗引擎、战斗阶段处理、战斗动作和战斗结果。
- 演习/战役都复用的规则归一化和准备页公共步骤只保留一份。

### `common`

- 设备连接、截图、点击、滑动和进程操作。
- OCR、OpenCV、模板匹配、ROI、坐标和静态资源。
- 不知道 `task_type`、不持有任务状态、不做演习或战役决策。

### 治理原则

- 执行器直接调用共享导航，不在每个业务里重复包 `goto`。
- `Operations` 只组合当前业务页面动作；有独立页面边界、断点或重试语义的方法可以保留。
- 不为了表面统一合并演习和战役执行器。
- 发现公共能力仍放在业务目录时，迁移到 `application`；设备和视觉实现继续位于 `common`。
- 所有新增或修改的执行器使用分组注释：
  `# ── 初始化 ──`、`# ── 主流程 ──`、`# ── 进度与断点 ──` 等。
- 每个实际业务步骤前写一条短注释；不为单行转发增加无意义方法。
- 新增日志统一使用 `[EnglishModule] 中文消息`，本链路标点保持一致。

## 三、演习标准 YAML

### 公共格式

```yaml
task_type: exercise
fleet_id: 2
formation: 2
night: false
sl_when_failed: false
formation_strategy: fixed
enemy_rules: []
enemy_formation_rules: []
fleet:
  - 舰船A
  - 舰船B
  - 舰船C
  - 舰船D
  - 舰船E
  - 舰船F
```

### 字段约束

| 字段 | 必填 | 约束 |
|---|---:|---|
| `task_type` | 是 | 固定为 `exercise` |
| `fleet_id` | 是 | 整数 `1-4`，表示选择的队伍 |
| `formation` | 否 | `1-5`，默认 `2`（梯形） |
| `night` | 否 | 布尔值，默认 `true` |
| `sl_when_failed` | 否 | 布尔值，默认 `false`；与战果识别联动，默认战果达到 A 不 SL |
| `formation_strategy` | 否 | 当前默认 `fixed`；`by_opponent` 只作为后续扩展，不在本批执行 |
| `enemy_rules` | 否 | 列表；字段形态沿用现有规则，敌方舰种 OCR 消费留 TODO |
| `enemy_formation_rules` | 否 | 列表；字段形态沿用现有规则，敌方阵型 OCR 消费留 TODO |
| `fleet` | 否 | 固定舰船名称列表，最多六个槽位；与 `fleet_presets` 互斥 |

执行次数由入口 `count` 提供，不写入 YAML。`discard`、`exercise_times`、`robot`、
`max_refresh_times` 没有现成消费链，本批不加入标准 YAML。

### 编队和校验

- `fleet_id` 是演习、普通战斗、活动战斗的队伍编号；战役和决战不得依赖该字段。
- `fleet` 使用现有固定编队格式；主选/备选、舰种、等级和严格/宽泛规则由现有舰队模型校验。
- `fleet` 与 `fleet_presets` 同时出现时拒绝入队；空列表、超过六槽或非法字段拒绝入队。
- `task_type` 必须进入选船模块；演习使用通用编队分支，战役使用固定物理槽位分支，决战使用决战分支。
- `enemy_rules`、`enemy_formation_rules` 本批只完成格式校验和计划保留，不伪造未接入的对手 OCR 行为。

## 四、演习 E2E

每次 E2E 都必须：初始化游戏 → 进入首页待机 → 执行场景 → 无论成功或失败都回到首页。
游戏进程异常退出时重新初始化；不重放已完成点击。

至少验证：

1. 标准 YAML 读取、`task_type`/`fleet_id`/`formation`/`night` 约束。
2. 队伍切换和 `fleet` 编队；第一次可验证同一主选配置复用，后续切换队伍验证换船。
3. 演习导航、对手选择、出征准备、编队、夜战、结算和下一对手流程。
4. 演习安全断点：入口、进入编队、一次选船完成、出征前、战斗结束后。
5. 断点处插入远征或奖励任务，完成后恢复演习；检查连续任务和非连续任务的导航交接。
6. 演习日志格式、对手编号、编队、OCR 和战斗结果日志。

实机次数严格按现有设备/游戏次数和既有任务书限额执行；先完成静态验证，不为调试重复消耗次数。

## 十、第一轮顶层代码治理（追加阶段，2026-09-04）

### 目标

`autowsgr` 顶层只保留五个架构层目录：`server`、`dispatch`、`business`、
`application`、`common`。现有 `infra`、`ops`、`scheduler`、`ui`、`constants`、
`contracts` 按职责拆入这五层；本轮只做粗粒度归位和导入收口，不重写业务流程。

### 归位原则

- `infra` 的设备、视觉、系统和资源实现归 `common`；运行时上下文归 `application`。
- `ui` 的页面和导航能力归 `application`；旧导出只保留在该层的兼容位置。
- `ops` 的业务用例归 `business`；启动和运行时编排归 `application`。
- `scheduler` 的任务队列和触发器归 `dispatch`；启动器归 `application/runtime`。
- `constants`、`contracts`、共享类型归 `common`。

### 非目标

- 本轮不拆分每个页面内部职责，不重写战斗/演习/战役业务规则。
- 本轮不修改 GUI 契约，不删除仍有明确消费者的旧行为；兼容入口只作为过渡壳。
