# 活动域与活动导航器设计

> 状态：**讨论中，未定稿**（2026-10-01 记录）。本文件只记录已确认的设计方向，不代表已实现。
> 本次适配目标：**推图活动**。

## 1. 目标

把「游戏活动」做成可复用框架：**流程通用，换一期活动只改模板 / 坐标 / ROI**；不同玩法
（活动类型）走不同链路。

已知活动玩法（用户列举，非穷尽）：

- 舰队问答
- 普通推图（本次适配目标）
- 立体强袭

## 2. 两个正交维度

| 维度 | 决定什么 | 变化频率 |
| --- | --- | --- |
| 玩法（event type） | 走哪条链路、调用哪些方法 | 换玩法才变 |
| 期（event id） | 模板、坐标、ROI | 每期活动都变 |

框架的意义就是让这两维各自独立变化。

## 3. 任务侧契约（用户已确认）

- YAML 任务用 **task type** 区分；
- `task type = event` 时，**额外增加 event type** 判断是哪类活动，从而走不同链路；
- event type **由上层决定**，写在 YAML 任务里，不是运行时自动识别。

## 4. 活动导航器逻辑（用户已确认）

**event checker 也是导航器的一部分。**

链路：`X 页面 → 活动入口 → 活动地图`，活动入口怎么进入由 YAML 决定。

导航器步骤：

1. 先判断「要进入活动入口」；
2. 看活动是什么类型；
3. 按类型走不同路径（不同类型路径不同）；
4. **先回首页** —— 所有活动入口都在首页；
5. 调用**首页 UI 控制器**，点击进入；
6. 按活动类型加载 checker：本次是推图，则判断当前活动地图的**标题**；
   - 默认预期是**普通模式**的标题；
   - 为稳妥，也要能识别**困难模式**的标题；
7. **导航器职责到此结束**，后面归 UI 控制器。

## 5. 层间职责

| 层 | 负责 | 按玩法分？ |
| --- | --- | --- |
| 导航器 | 页面身份判定、路径选择、触发页面动作 | event checker 按活动类型加载 |
| UI 控制器 | 活动页面的识别与业务流程；不同活动类型调用不同方法 | 分 |
| 常量 / 资源 | 模板、坐标、ROI | 按期（event id）组织 |

## 6. 本次采集并已验证的事实

活动地图页的两种状态（实测）：

| 状态 | 锚点 | 说明 |
| --- | --- | --- |
| 干净地图页 | 左下角模式按钮 | 明亮可见；文字是**要切换到的**模式（显示「普通模式」⇒ 当前在困难图） |
| 出征浮窗打开 | 出击准备按钮 | 整页被暗色蒙版压暗、模式按钮下半截被浮窗底栏压住，模式按钮模板失效 |

其他事实：

- 地图标题：普通模式为「最强之舟」，困难模式为「最强之舟（困难）」。
- 本活动 6 个关卡点坐标与旧实现里的两套（通用一套、`20260730` 一套）**都不同**，属本活动专属布局。
- 旧 `controller/home/event_page/` 使用旧 API（`vision.ImageChecker`、`application.vision.resources.pages.event`、`UIContext`）；
  其 `calibration.py` 与 `data/calibration/*.yaml` **零调用方**，且与 `constants.py` 重复定义同一批坐标。

## 8. 基建侧的新契约（实现时使用）

另一个 Agent 已落地 `0fa2171 feat(vision): add the shared recognition entry to common.vision`，
视觉调用统一走 `common.vision` 的公共入口：

- 取图：`shot(ctx)`
- 前识别（等到出现）：`before_template` / `before_ocr` / `before_pixels`
- 后识别（等到消失）：`after_template` / `after_ocr` / `after_pixels`
- 调用方只提供识别数据、识别规则和预期；`ContextHandle` 由 dispatch 统一提供。

这取代了此前 `application.ui.recognition_flow` 的角色；新 checker 应使用该公共入口。
