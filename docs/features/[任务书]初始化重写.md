## 0. 目标与范围

把「启动游戏 → 登录 → 主页 → 清浮层」整条链路重写，归属 dispatch，并删掉旧实现。

**做**：新增 `autowsgr/dispatch/startup.py`；按新导航器重写启动链路；区服选择接入；
`login_checker` 补齐后识别与识别参数；调用方切换；删除 `application/runtime/startup.py` 与
`application/runtime/initialize/`。

**不做**：`common/vision` 的改动（识别机制保持现状）；`launcher.py` 改名；业务执行器自身的其余改造。

## 1. 模块归属（用户 2026-10-11 定）

| 职责 | 归属 |
| --- | --- |
| 进程 bootstrap：配置加载、日志初始化、连接设备、构造 RuntimeContext | 留在 `application/runtime/launcher.py`，**名字不改** |
| 游戏启动与幂等初始化 | 新增 `autowsgr/dispatch/startup.py` |
| 何时启动程序、何时 SL | **dispatch 处理器决定并调用**；业务执行器只上报问题 |

`launch()` 的 `ensure_game` 参数删除，改成调用方显式两步：`ctx = launch(...)` → `ensure_ready(ctx)`。

## 2. 旧流程盘点（业务链路保留，代码重写）

旧实现散在三处、两份重叠：

```text
[launcher] 配置 → 日志 → 连设备 → 造 RuntimeContext
    └→ startup.ensure_game_ready()          398 行

[dispatch.processor / business.bettle.executor]
    └→ initialize.initialize()              362 行（含 overlays / updater）
```

以 `initialize` 的业务契约为准（严格判定 + SL + 更新钩子）；`startup` 的宽松判定丢弃。

### 2.1 必须保留的业务契约

| 契约 | 内容 |
| --- | --- |
| 幂等 | 任意状态进来，出去必定是「主页 + 浮层已清 + 待机」；SL 与异常恢复复用同一入口 |
| 任务默认从首页开始 | 每个任务开始前都回到主页，不做任务间状态复用（用户 2026-10-11 定） |
| SL 只重启一次 | 防死循环；仍失败抛错交处理器 |
| 浮层成功才标记 | 三个弹窗都关干净才记录已处理；中途失败不记录，报错交处理器（用户 2026-10-11 定） |

### 2.2 必须保留的业务参数

| 参数 | 旧值 | 落点 |
| --- | --- | --- |
| 等健康游戏提示出现 | 120s，1s 轮询 | `startup`：`attempts=120, interval_seconds=1.0` |
| 点进入后等主页 | 30s | `startup`：`attempts=30, interval_seconds=1.0` |
| 恢复主页面超时 | 20s，1s 重试 | `startup`：`attempts=20, interval_seconds=1.0` |
| 强杀后等进程退出 | 2s | `startup`：`_RESTART_SETTLE = 2.0`（硬 sleep） |
| 加载中再探一次 | 3s | `startup`：`_LOADING_RECHECK_WAIT = 3.0`（硬 sleep，用户定的兜底） |
| 浮层消除上限 | 5 次，每次 1.5s | 导航器每日弹窗前置流程 |

### 2.3 丢弃的部分

- `updater.py` 空实现 → 被「更新提示 → 报错」取代；
- `startup.wait_for_game_ui` 的宽松判定；
- 两套浮层实现合并成导航器的每日弹窗前置流程（进程级，成功才标记）；
- 业务执行器自己调 initialize 的写法。

## 3. 新链路设计

### 3.1 公开入口

```python
# autowsgr/dispatch/startup.py
def ensure_ready(ctx: ContextHandle) -> None:
    """执行器的永远第一步：任意状态 → 主页 + 浮层已清。幂等。"""
```

### 3.2 三分支（用户 2026-10-11 定）

```text
① 游戏没开          → _launch_game：完整冷启动链路
② 游戏开着但没有上下文 → 遍历 checker 定位当前位置 → 导航回主页（相当于 restart）
③ 已经在主页        → 处理每日弹窗；处理过则跳过，维护程序上下文
```

第 ② 条的"遍历 checker 定位"由导航器 `_detect_page` 提供（栈空时自动做），不新增实现。

### 3.3 主流程

```text
ensure_ready(ctx):
  ① 游戏没运行 → _launch_game(ctx)
  ② _reach_home(ctx)：NavigationService(ctx).navigate_to(PageName.HOME)
       （导航器自带：栈空遍历 checker 定位、经过首页跑浮层前置流程）
  ③ 失败 → _restart_game(ctx)（SL：强杀 + _launch_game，只一次）→ 再 _reach_home
  ④ 仍失败 → 抛错，交 dispatch 处理器处置

_launch_game(ctx):
  ① 取包名（配置 account.game_app）→ start_app
  ② check_black_screen(attempts=120, interval_seconds=1.0)          前识别：等到出现
  ③ check_black_screen(absent=True, attempts=…, interval_seconds=…) 后识别：等到消失
  ④ 分支一 · 更新：
       后识别「需要更新」通过 → 没有更新，进入分支二；
       后识别失败 → 前识别「需要更新」→ 通过则抛 ManualRepairRequiredError；
       两个都不成立 → 状态不明，抛错
  ⑤ 分支二 · 加载：
       后识别「正在进入港区」通过 → 加载结束，进入下一步；
       前识别通过 → 仍在加载 → 硬 sleep 3s，再做一次后识别
  ⑥ 前识别「登录页」（进入游戏模板与换区入口模板二选一）
  ⑦ _select_server(ctx)（见 §5）
  ⑧ 点「进入游戏」→ 后识别「进入游戏」模板消失
  ⑨ 回到 ensure_ready ② 确认主页
```

## 4. 识别参数设计（用户 2026-10-11 定）

### 4.1 参数与落点

前后识别的模板与识别方法相同，区别只有判定模式；**模式与节奏都由调用方决定**。

| 参数 | 语义 | 默认值 | 谁传 |
| --- | --- | --- | --- |
| `absent` | `False` = 前识别（要它出现）；`True` = 后识别（要它消失） | `False` | 调用方 |
| `attempts` | 识别次数 | `1`（单帧） | 调用方 |
| `interval_seconds` | 每次失败后的间隔 | `0.5`（与 `common.vision` 一致） | 调用方 |

默认值保证导航器行为不变（什么都不用传）；要长等待的调用方自己传。

### 4.2 传递链路

```text
调用方（startup / 导航器）
    │  absent, attempts, interval_seconds
    ▼
login_checker.check_black_screen(ctx, *, absent, attempts, interval_seconds)
    │  原样透传，不做判断
    ▼
login_checker.recognition.is_black_screen_visible(ctx, *, absent, attempts, interval_seconds)
    │  ← 唯一的那一个 if：absent 决定用哪个 vision 入口
    ▼
common.vision.expect_template / expect_template_absent(ctx, …, attempts, interval_seconds)
    │
    ▼  截图 → 识别 → 不满足 → sleep(interval) → 重试到 attempts
```

`common.vision` **不改**：保留成对入口和自己的默认参数，只负责识别机制。

### 4.3 checker 侧的改动

`login_checker` 的八个画面入口统一加三个可选参数，并补四个后识别能力（同一入口 + `absent=True`）：

```text
黑屏健康提示 / 更新提示 / 加载中 / 登录页 / 区服选择页 / 区服定位 / 两个按钮中心
```

其中需要"判断消失"的场景由调用方传 `absent=True` 表达，不新增入口。

## 5. 区服选择（用户 2026-10-11 定）

### 5.1 配置

```yaml
account:
  # game_app: 官服          # 大部分用户是官服，需要换渠道服时再打开
  game_server: 默认         # 默认 / 胡德 / 俾斯麦 / 昆西 / 长春
```

- 字段名 `game_server`；"默认"= 不处理换区；
- `game_app` 在示例配置里注释掉（代码内保留默认值 `GameAPP.official`）。

### 5.2 运行期状态

区服选择状态是**进程级**，放 `dispatch/session.py` 的 `SessionState`：

- 程序启动时为空 → 按用户设置选择一次；
- 程序运行中 SL 不再选择（上下文已有）；
- **程序重启后重新选择**（进程级状态随进程消失）。

### 5.3 换区流程

```text
_select_server(ctx):
  若 session.server_selected → 返回
  若用户设置为「默认」→ 标记已选，返回
  index = login_checker.find_server_position(ctx, 用户设置区服)
  index 为空 → 用已知序号兜底（0 胡德 / 1 俾斯麦 / 2 昆西 / 3 长春）
  ① 点「点击换区」→ 后识别「进入游戏」模板消失
  ② 点对应区服条目 → 后识别「切换大区」模板消失
  ③ 标记 session.server_selected
```
