| 职责 | 归属 |
| --- | --- |

## 2. 旧流程盘点（业务链路保留，代码重写）

旧实现散在三处、两份重叠：

```text
[launcher] 配置 → 日志 → 连设备 → 造 RuntimeContext
    └→ startup.ensure_game_ready()          398 行

[dispatch.processor / business.bettle.executor]
    └→ initialize.initialize()              362 行（含 overlays / updater）
```

以 `initialize` 的业务契约为准（严格判定 + SL + 更新钩子）；`startup` 的宽松判定丢弃。

### 2.1 必须保留的业务契约

| 契约 | 内容 |
| --- | --- |
| 幂等 | 任意状态进来，出去必定是「主页 + 浮层已清 + 待机」；SL 与异常恢复复用同一入口 |
| 任务默认从首页开始 | 每个任务开始前都回到主页，不做任务间状态复用（用户 2026-10-11 定） |
| SL 只重启一次 | 防死循环；仍失败抛错交处理器 |
| 浮层成功才标记 | 三个弹窗都关干净才记录已处理；中途失败不记录，报错交处理器（用户 2026-10-11 定） |
| SL 后导航栈作废 | 游戏被强杀重开后，栈顶那个页面已经不存在；`restart_game` 必须重置导航栈，否则后续 `navigate_to` 会被"已在目标页面"短路掉 |

### 2.2 必须保留的业务参数

| 参数 | 旧值 | 落点 |
| --- | --- | --- |
| 等健康游戏提示出现 | 120s，1s 轮询 | 导航器 `ensure_started`：`attempts=120, interval_seconds=1.0` |
| 点进入后等主页 | 30s | 导航图确认表：`HOME` 的确认节奏 `attempts=30, interval_seconds=1.0` |
| 恢复主页面超时 | 20s，1s 重试 | `dispatch`：导航失败后 SL 一次、再导航一次 |
| 强杀后等进程退出 | 2s | 导航器 `restart_game`：硬 sleep |
| 加载中再探一次 | 3s | 导航器 `ensure_started`：硬 sleep（用户定的兜底） |
| 浮层消除上限 | 5 次，每次 1.5s | 导航器每日弹窗前置流程 |

### 2.3 丢弃的部分

- `updater.py` 空实现 → 被「更新提示 → 报错」取代；
- `startup.wait_for_game_ui` 的宽松判定；
- 两套浮层实现合并成导航器的每日弹窗前置流程（进程级，成功才标记）；
- 业务执行器自己调 initialize 的写法。

## 3. 新链路设计（方案甲，用户 2026-10-11 定）

### 3.1 垂直调用链

```text
dispatch/startup.py   ensure_ready()      只决定「何时启动、何时 SL」
        ↓
navigation/service.py ensure_started() / restart_game() / navigate_to()
        ↓
checker（识别）与 controller（点击）
```

启动段（黑屏 / 更新 / 加载）没有可用的边：没有点击动作，也不是导航目标，因此由导航器自己的
入口承担，而不是塞进可达列表。

### 3.2 导航器侧新增

```python
class NavigationService:
    def ensure_started(self) -> None:
        """把游戏带到「登录页」；能走导航图的转移都走导航图。"""

    def restart_game(self) -> None:
        """SL：强杀游戏后重新走一遍 ensure_started。"""
```

`ensure_started` 内部流程：

```text
① 游戏没运行 → start_app(包名)
② check_black_screen(attempts=120, interval_seconds=1.0)               等健康提示出现
③ check_black_screen(absent=True, attempts=10, interval_seconds=1.0)   等它消失
④ 更新分支：后识别通过=没更新；前识别通过 → 抛 ManualUpdateRequiredError
⑤ 加载分支：后识别通过=加载完；前识别通过 → 硬 sleep 3s，再后识别一次
⑥ check_login_page(attempts=60, interval_seconds=1.0)                  等登录页
⑦ _select_server()：需要换区时 navigate_to(SERVER_SELECT) → navigate_to(LOGIN_PAGE, position=index)
```

换区复用导航图现成的两条边；黑屏/更新/加载是"游戏自己切画面"，只能在这一层处理。

### 3.3 dispatch 侧

```python
def ensure_ready(ctx) -> None:
    """执行器的永远第一步：任意状态 → 主页 + 浮层已清。幂等。"""
    navigator = NavigationService(ctx)
    if not 游戏在运行:
        navigator.ensure_started()
    try:
        navigator.navigate_to(PageName.HOME)
    except ManualUpdateRequiredError:
        raise ManualRepairRequiredError('请手动完成游戏更新') from None
    except NavigationError:
        navigator.restart_game()
        navigator.navigate_to(PageName.HOME)
```

三分支统一收口在 `navigate_to(HOME)`：游戏没开 → 先 `ensure_started`；开着在别的页 → 导航器自己
定位并拼路径；已经在主页 → 短路返回。

**到主页与清浮层的先后（用户 2026-10-11 定）**：`navigate_to(HOME)` 走完 `登录页 → 主页面` 这条边
（即点一次「进入游戏」）之后，**先识别并处理每日浮窗，最后才确认主页**。原因：浮窗要等进入主页才出现，
在登录页那一步就处理会把「今日已处理」的标记消耗在浮窗尚不存在的时候。

「需要更新」**不走 SL**：重启多少次都一样，直接转成处理器要抛的错误。

### 3.4 navigation 侧配套改动

| 位置 | 改动 |
| --- | --- |
| `navigation/types.py` | 新增 `ManualUpdateRequiredError(NavigationError)` |
| `navigation/registry.py` | `_PAGE_CHECKERS` 直接放各页面的确认入口，不再包一层配节奏 |
| `home.check_home_page` | 加 `attempts` / `interval_seconds`（与 login 一致，供导航图配节奏） |

### 3.6 点击落点规则（用户 2026-10-11 定）

| 页面 | 落点来源 |
| --- | --- |
| **活动页**（活动地图、活动章节浮窗） | **保持现状**：模板与坐标每期活动都要在框架里适配，等新活动出来再逐期补（用户 2026-10-11 定） |
| **其他模块**，且有模板匹配 | **模板中心 + 固定坐标兜底**（识别不到时退回静态落点） |
| **其他模块**，没有模板匹配 | **静态坐标** |

## 4. 识别参数设计（用户 2026-10-11 定）

### 4.1 参数与落点

前后识别的模板与识别方法相同，区别只有判定模式；**模式与节奏都由调用方决定**。

| 参数 | 语义 | 默认值 | 谁传 |
| --- | --- | --- | --- |
| `absent` | `False` = 前识别（要它出现）；`True` = 后识别（要它消失） | `False` | 调用方 |
| `attempts` | 识别次数 | `1`（单帧） | 调用方 |
| `interval_seconds` | 每次失败后的间隔 | `0.5`（与 `common.vision` 一致） | 调用方 |

默认值保证导航器行为不变（什么都不用传）；要长等待的调用方自己传。

### 4.4 执行器（用户 2026-10-11 定）

路径的"走出去"从 `service._walk` 提成独立模块 `navigation/executor.py`：它是导航的
**实际执行器**，而 `navigate_to` / `navigate_back` 只是入口（决定去哪、怎么算路）。

```python
class NavigationExecutor:
    def walk_forward(self, path, params) -> None:
        """前进：从当前页走向目标页；边的动作可接收调用方参数。"""

    def walk_backward(self, path) -> None:
        """后退：从当前页退回上一页；不接受参数。"""
```

**自动前后识别**：一次点击的语义天然成对——旧页面的标志应当消失，新页面的标志应当
出现。执行器同时掌握"离开谁"（压栈前的栈顶）与"去往谁"（边的目标），因此由它统一
决定用哪种识别，**边与 checker 都不声明**：

| 时机 | 识别 | 对象 |
| --- | --- | --- |
| 动作之后、压栈之前 | **后识别**（前识别取反） | 栈顶那一页的标志应当消失 |
| 动作之后、压栈之前 | **前识别** | `edge.target` 的标志应当出现 |

- **识别节奏定义在 checker 自己**：每个确认入口的 `attempts` / `interval_seconds` 默认值就是"这个页面怎么认"的一部分（登录页 10×0.5s、首页 30×1s），调用方要覆盖时传参；registry 不兼职配节奏；
- 没有确认入口的页面（`_PAGE_CHECKERS` 未覆盖）直接放行；
- **不给 checker 加 `absent`**：后识别就是前识别取反，二者等价；
- **不维护 previous**："离开谁"永远是压栈前的栈顶。

`service` 保留：`navigate_to` / `navigate_back`、`_current_page` / `_detect_page`、
`ensure_started` / `restart_game` / `_select_server`、每日浮窗；浮窗经 `on_arrive` 钩子
注入执行器，在"到达主页之后、确认主页之前"执行。

### 4.2 传递链路

```text
调用方（startup / 导航器）
    │  absent, attempts, interval_seconds
    ▼
login.check_black_screen(ctx, *, absent, attempts, interval_seconds)
    │  原样透传
    ▼
login.recognition.is_black_screen_visible(ctx, *, absent, attempts, interval_seconds)
    │  原样透传
    ▼
common.vision.expect_template(ctx, …, absent, attempts, interval_seconds)
    │  ← 唯一的那一个 if：absent 决定断言方向
    ▼  截图 → 识别 → 断言 → 不满足 → sleep(interval) → 重试到 attempts
```

### 4.3 vision 的改动（用户 2026-10-11 定）

前后识别的循环、截图与重试节奏完全一致，只有最后断言相反，因此统一到一个入口：

| 入口 | 前识别（`absent=False`） | 后识别（`absent=True`） |
| --- | --- | --- |
| `expect_template` | 命中数 `>= min_matches` | 命中数 `< min_matches` |
| `expect_ocr` | 文本命中期望 | 文本不命中期望 |
| `expect_pixels` | `result.matched` | `not result.matched` |

- 三个入口新增 `absent: bool = False`；
- **删除** `expect_template_absent` / `expect_ocr_absent` / `expect_pixels_absent`（生产代码 0 调用方，仅测试与文档引用）；
- `attempts` / `interval_seconds` 保持 vision 自己的默认（3 次 / 0.5s）。

同批同步：`common/vision/__init__.py`、`vision.md`、worktree 的 `AGENTS.md`、
`testing/vision/test_recognition_flow.py`、`testing/common/vision/test_service.py`。

### 4.3 checker 侧的改动

`login` 的八个画面入口统一加三个可选参数，并补四个后识别能力（同一入口 + `absent=True`）：

```text
黑屏健康提示 / 更新提示 / 加载中 / 登录页 / 区服选择页 / 区服定位 / 两个按钮中心
```

其中需要"判断消失"的场景由调用方传 `absent=True` 表达，不新增入口。

## 8. 流程重构：初始化与导航器的边界（用户 2026-10-12 定）

本节取代 §3.2 / §3.4 关于 `ensure_started` / `restart_game` 的描述。

### 8.1 分工

| 角色 | 职责 |
| --- | --- |
| `dispatch/startup.py` | 拉起 APP、决定是否 SL、按配置决定是否换区；只调用下面 UI 层的入口 |
| `NavigationService.navigate_to_login()` | 把**处于启动阶段**的游戏带到登录页；已经在某个页面上时原样返回（幂等）。**不负责拉起 APP** |
| `NavigationService.navigate_to(...)` | 页面之间的导航，含换区（登录页 ↔ 区服选择页）与回主页 |
| checker / UI 控制器 | 识别与点击 |

**dispatch 不出现 checker 调用**：启动段要用 checker，所以它住在 UI 层，dispatch 只挑调用。

### 8.2 四种入口场景

| 场景 | 处理 |
| --- | --- |
| 冷启动（APP 从未启动） | 拉起 APP → `navigate_to_login()` → 换区（按配置）→ `navigate_to(HOME)` |
| APP 在跑、脚本刚起、在首页 | 不拉 APP、**不调 `navigate_to_login`**；直接 `navigate_to(HOME)` 短路并顺带清浮窗 |
| APP 在跑、脚本刚起、不在首页 | 同上；`navigate_to(HOME)` 遍历 checker 认出当前页并拼路径回家 |
| 认不出任何页面（奇怪页面） | SL（见 §8.5） |
| SL（脚本还活着、游戏被杀） | 同「认不出」 |

脚本刚启动时**选区上下文为空是允许的**；`navigate_to_login` 只在游戏处于启动阶段时调用。

### 8.3 启动三信号（由游戏特性决定）

| 信号 | 特性 | 处理 |
| --- | --- | --- |
| 黑屏（健康游戏提示） | 能否识别到不重要 | 识别不到 → `sleep 3`，继续下一项 |
| **更新提示** | **唯一硬分支**：弹出即游戏卡死 | **识别到 → 立刻抛错交人工处理** |
| 加载中 | 宽泛校验 | 识别不到 → `sleep 3` |
| 登录页 | — | 这里才需要重试等待 |

### 8.4 换区

- 用户配置为「默认」→ **跳过换区**，不碰 checker；
- 配置为固定区服 → `navigate_to(SERVER_SELECT)` → `navigate_to(LOGIN_PAGE, server=<区服名>)`；
- 位置由「OCR 逐条比对 + 序号兜底」在注册表内部现算，调用方只传区服名；
- 本次运行已选过（`server_selected`）→ 跳过。

### 8.5 SL 规则

- 由 dispatch 执行：需要 SL 时 `stop_app` → 等进程退出 → **清页面栈** → 重新拉起 APP → 走冷启动流程；
- **清页面栈**：SL 后之前的导航信息必然作废；
- **选区上下文保留**：游戏重开后按逻辑会默认进上次选的区服，因此有上下文即跳过换区；没有上下文则按用户配置执行换区；
- 初始化脚本接受一个「是否需要 SL」的参数。

### 8.6 导航器保留什么

`navigate_to`、`navigate_back`、`navigate_to_login`、页面识别，以及**到主页时顺带清浮窗**（浮窗是「到主页」的内部流程，不放区服路径里）。
删除 `restart_game` 与 `ensure_server_selected`。

## 9. 每日浮窗走导航链（用户 2026-10-12 定）

浮窗不再由 `service` 里的私有流程处理，改成**几个普通页面 + 几条普通边**：一切皆是页面，一切都走导航图。

### 9.1 三个浮窗页

| `PageName` | 画面 |
| --- | --- |
| `HOME_NEWS` | 主页上有每日公告浮窗 |
| `HOME_REWARD` | 主页上有每日奖励（签到）浮窗 |
| `HOME_REWARD_CONFIRM` | 奖励领取后的确认浮窗 |

### 9.2 主页确认要排除浮窗

`check_home_page` 改成「**没有浮窗的主页**」：主页模板命中，且公告、奖励、确认三个浮窗都不在。
原因：现在奖励浮窗存在时它照样返回真，于是 `navigate_to(HOME)` 一看「起点即目标」就短路，注册好的浮窗链永远走不到。
底层 `recognition.is_home_page_visible` 保持「只看主页模板」，不动。

### 9.3 链

```text
每日公告 → 每日奖励 → 每日奖励确认 → 主页
```

每一步的动作都是「**先问 checker 再动手**」：

| 边 | 动作 |
| --- | --- |
| 每日公告 → 每日奖励 | 有公告就关闭（勾选框按需勾上），没有就什么都不做 |
| 每日奖励 → 每日奖励确认 | 有奖励就点领取，没有就什么都不做 |
| 每日奖励确认 → 主页 | 有确认浮窗就点确认，没有就什么都不做 |

**空点问题由此消失**：每一步都先确认画面在不在，不在就跳过，不会点到别的东西。

### 9.4 除链尾外都不做到达确认

给边加一个开关：

```python
@dataclass(frozen=True, slots=True)
class NavTarget:
    target: PageName
    action: Callable[..., None]
    description: str = ''
    confirm: bool = True      # 到达后是否确认；浮窗链的中间步置 False
```

执行器在 `confirm=False` 时跳过到达确认，直接把目标页压栈。需要关掉确认的边有两类：

- **进链的边**（登录页 / 出征页 / 活动地图 → 主页）：不管有没有浮窗，进了主页就算到；
  照常确认的话，当天公告已关时会直接失败并触发 SL（实机踩过）。
- **链内的中间步**：「到了吗」取决于下一个浮窗在不在，静态判不了。

**只有链尾「每日奖励确认 → 主页」做真确认。**

### 9.5 所有回主页的边改指向每日公告

把原来指向 `HOME` 的边改成指向 `HOME_NEWS`，这样「从活动页回家」也会顺手把浮窗清掉：

```text
活动地图 → 每日公告 → 每日奖励 → 奖励确认 → 主页
```

没有浮窗时前几步全部空转（动作各自跳过、确认各自跳过），最后照常确认主页——所以这条链**在无浮窗时也是安全的**。

### 9.6 三种画面

| 画面 | 走法 |
| --- | --- |
| 只有公告 | 认出「每日公告」→ 关公告 → 奖励步跳过 → 确认步跳过 → 确认主页 ✓ |
| 公告 + 奖励 | 认出「每日公告」→ 关公告 → 领奖励 → 点确认 → 确认主页 ✓ |
| 什么都没有 | 认出「主页」→ 起点即目标 → 短路 ✓ |

### 9.7 删除

`service._handle_daily_popup` / `_handle_daily_news` / `_handle_daily_reward` 全部删除；
「每日一次」的 `SessionState.daily_popup_handled` 标记也不再需要（浮窗在就走链、不在就短路，天然幂等）。

### 9.8 已知边界

- 浮窗目前**只弹在主页**，所以「有浮窗 ≈ 在主页」这个简化成立；哪天非主页也弹浮窗，需要重新设计（例如引入浮窗栈）。
- 奖励浮窗会被旧的 `check_home_page` 认成主页——这正是 §9.2 要修掉的那条。
