# 导航器治理任务书

日期：2026-09-05
范围：`AutoWSGR/autowsgr/application/ui/navigation` 及其直接调用方。

## 目标

整理导航器的代码结构、注释和职责边界，确认导航器与 UI 操作层的依赖关系，
并把可复用的维护规则沉淀为项目规范。所有改动以当前架构纪要和仓库
`pre-commit` 规则为准；两者冲突时，以 `pre-commit` 为准。

## 需求清单

### 1. 导航图与格式

- [x] `graph/common.py`、`graph/combat.py`、`graph/logistics.py` 中，导航边使用独立拓扑区块；
  回调 `def` 按 Python 可执行顺序放在拓扑常量之前。
- [x] 所有 Python 文件连续空行不超过两行；若与 `pre-commit` 冲突，以钩子结果为准。
- [x] 用 `# ── XXX ─────────────────────────────────────────────────` 形式划分功能入口、
  功能实现和同类方法区域。

说明：`NavEdge` 常量需要绑定已定义的回调函数，完整边集合不能在 `def` 前直接构造；
当前以“动作定义 → 拓扑常量”的可执行顺序实现，并用分区标题保持拓扑与动作的清晰边界。

### 2. 导航器注释

- [x] 每个导航文件开头说明文件职责、调用方式和直接依赖。
- [x] 简单函数使用一行注释；有明显流程的函数使用 `1、`、`2、`、`3、` 表述关键步骤。
- [x] 注释使用业务语言，避免重复代码和堆叠专业术语。

### 3. 项目规范

- [x] 将本轮空行、代码分区、函数注释和依赖说明规则泛化为独立项目规范文档，
  保存到本目录。

### 4. 导航图实际链路

- [x] 从 `goto_page` 开始追踪 graph 的路径查找、页面识别、点击、等待和到达检查。
- [x] 列出实际使用的 `common` 能力和每项能力的调用位置。

### 5. 导航器与 UI 操作边界

- [x] 区分导航器负责的入口导航和 UI 操作负责的业务页面动作。
- [x] 检查业务层是否直接同时调用导航器与 UI 操作；判断现有依赖是否符合垂直分层。
- [x] 评估仅导航器使用的底层能力是否应留在 `common`，还是应由 `application` 聚合。

结论：导航器负责跨页面路径和入口交接，`application/ui/pages` 负责页面内动作；
被多个页面或业务复用的 common 能力继续留在 common。业务层的少量 common 直调用列为后续边界治理，
本轮不增加纯转发层。

### 6. UI 操作 application 入口评估

- [x] 评估 UI 操作是否需要像导航器一样提供面向业务层的 application 入口。
- [x] 给出保留现状、增加薄入口或调整职责的结论，并说明依据和后续条件。

结论：现有 `application/ui/pages` 已是业务可调用的 UI application 入口，不新增
`application/ui/operations.py`。只有出现跨多个页面的真实 UI 流程时，才增加一个有业务语义的 application 方法。

### 7. 注释依赖路径整改

- [x] 导航目录每个文件头明确列出 canonical 依赖的完整 Python 包路径。
- [x] 关键函数注释明确指出调用的页面类、方法或下层模块路径，不能只写简称。
- [x] 保持业务语言和简洁表达，不硬编码机器绝对路径。

结论：文件头说明“负责什么、谁调用、依赖什么路径”，函数说明业务动作；不把完整
包路径堆进每一行函数注释。连续空行最多两行，分区统一使用 `# ── ... ───`。

## 执行规则

1. 完成每一项需求后，重新阅读本任务书并核对勾选项。
2. 先做静态分析和最小代码整理，再运行一次针对性测试；不进行实机操作。
3. 不恢复或覆盖用户未暂存修改；所有代码改动必须留下可审查的 Git diff。
4. 发现任务书与架构纪要冲突时暂停该项，记录冲突并提交报告，不自行猜测。
