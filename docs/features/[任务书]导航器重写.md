## 0. 目标

重写导航器：**统一入口 + 可达列表注册 + 私有执行 + 前置流程**。调用方向严格单向：
**导航器 → 控制器**。

## 1. 边界（用户已确认）

| # | 边界 |
| --- | --- |
| 1 | 导航器 → 控制器单向；控制器只管点击与部分 checker，不反向依赖导航器 |
| 2 | **确认由 checker 决定**：checker 已经保证"能 check 到 / check 不到"，导航器不再二次确认 |
| 3 | 导航器内部按页面维护**可达列表**，由导航器持有与维护 |
| 4 | 路径拼接用列表（邻接表 + 广度拼接），不做复杂图算法 |
| 5 | `go_back` 回到**上一个页面**（导航栈） |
| 6 | 失败**抛给处理器**：处理器遍历所有 checker 定位当前页面，全找不到就重启 app 重新初始化；本次不评估 dispatch 是否持有错误信息 |

## 3. 核心设计

### 3.1 可达列表（getter list，一个文件）

`registry.py` 里只有"极个别私有点击函数 + 各页面的可达列表 + 查询方法"：

```python
# 页面 → 到达确认
_PAGE_CHECKERS: dict[PageName, Callable[[ContextHandle], bool]] = {...}

# 页面 → 可达列表
_NAV_TARGETS: dict[PageName, tuple[NavTarget, ...]] = {
    PageName.HOME: (
        NavTarget(PageName.EVENT_MAP, _home_to_event, '首页 → 活动'),
        NavTarget(PageName.SORTIE_MAP, _home_to_sortie, '首页 → 出征'),
    ),
    ...
}

def get_targets(page: PageName) -> tuple[NavTarget, ...]: ...
def get_checker(page: PageName) -> Callable[[ContextHandle], bool] | None: ...
```

- 列表**全部放一个文件**（约 30 条级别），不按页面拆文件 —— 拆散反而难查；
- `NavTarget` 带 `description`：给维护人和日志用（走错路时能看出走的哪条边）；
- 私有点击函数只写"极个别"，不为每条边写转发函数。

### 3.2 路径拼接

执行器只问"当前页能去哪"：`get_targets(当前页)` → 找到下一跳 → 再问一次，拼出有序路径。

### 3.3 确认

点击后用目标页的 checker 判断；checker 返回真即"到了"。**判断标准写在 checker 里**：导航器的确认表
统一收 `(ctx) -> bool` 的入口，不把判断标准漏到导航器。

活动地图的确认入口**新增** `check_event_map_page(ctx, *, event_type) -> bool`（内部读活动标题）；
它**不替代** `read_event_map_state` —— 后者仍供导航器读难度、业务层读状态。

### 3.4 传参

`goto_page(target, **params)` 把参数透传给该边的动作（例如活动章节 `stage`）。

### 3.5 前置流程（只在路径经过首页时跑）

起点是首页、目标是首页、或路径包含首页 —— 三种都算"经过首页"，此时才跑前置流程。

### 3.6 go_back

导航栈记录来路，回上一个页面；栈空或不可回退时抛错给处理器。

### 3.7 失败

执行器不自行恢复：单步失败向上抛，由处理器决定（定位当前页 / 重启 app）。

### 3.8 截图归属（前后识别都先截图再识别）

截图**由识别入口自己截**：`expect_*` / `expect_*_absent` 每轮重试都截图并 `record_screenshot`
缓存到上下文；调用方拿不到截图对象，因此不存在"在外面截一次再传进来"的路径。

### 3.9 第一条链路（推图活动出征）

```text
[前置] 路径经过首页 → 每日公告（存在 → 确认勾选（已勾选跳过）→ 关闭 → 确认消失）
                     → 每日奖励（存在 → 领取 → 确认浮窗 → 确认 → 确认消失）
[1] 首页 → 活动地图   点击 HomePage.go_to(Target.EVENT)；确认用 OCR 活动名称
[2] 活动地图内按需切难度
      识别难度按钮中心 → EventPage.switch_difficulty(center)
      后识别按钮模板消失 或 前识别地图名带"困难"，任一为真即算切换成功
[3] 活动地图 → 章节浮窗   点击 EventPage.go_to_overlay(node)；确认 check_event_sortie_prepare
[4] 章节浮窗 → 编队准备   点击 EventPage.go_to_prepare(center)；确认暂空（BATTLE_PREPARATION checker 至今未做，见 §10）
```

**难度与标题的判定**：普通地图 = 按钮显示"困难"、标题不带困难；困难地图 = 按钮显示"普通"、
标题带困难。标题**统一断言**：OCR 整个标题区域，文本里出现"困难"即为困难地图，不管括号形态。

**OCR 调用约定**：项目里 OCR 基本都是单行文字，调用时传 `recognition_profile='single_line'`；
判"困难"用 `expect_ocr`（没有多余模板，文字交给 FastOCR）。

## 4. 每日弹窗流程（两段解耦）

```text
[前置] 本次程序运行内未处理过 →
  ① 每日公告：存在 → 确认勾选（已勾选则跳过点击）→ 确认已勾选 → 关闭公告 → 确认公告消失
              不存在 → 跳过
  ② 每日奖励：存在 → 领取 → 确认浮窗 → 确认 → 确认奖励浮窗消失
              不存在 → 跳过
  ③ 两段都过完 → 标记"本次运行已处理"
```

公告跳过**不等于**跳过奖励，两段各自检测；由 service 的两个私有函数实现。

## 5. 进程级上下文（dispatch 子模块）

- 语义：**程序运行期内持久，重启消失**；因此每次开程序第一次经过首页都会重跑前置流程；
- 归属：dispatch 下新开子模块管理（拟 `dispatch/session.py`），与任务级 `context/` 并列；
- 必须同步维护 `[规范]dispatch-context临时规范.md` 与对应架构说明。

## 6. 活动域要点（原计划文档并入）

- 活动按**「玩法 × 期」**两维建模：玩法（推图 / 立体强袭 / 舰队问答）× 期号；
- event checker 归导航器；活动入口路径与活动玩法由 **YAML 任务**决定；
- 玩法标识：`stage_push`（推图，已实现）、`dimensional_assault`（立体强袭，TODO）、`fleet_quiz`（舰队问答，TODO）；
- 任务值形如 `event: stage_push`、`event_stage: EX7`，解析由业务层执行器调 `event.stage_push.parse_stage` 完成。

## 7. 约束与资源

**模板命名**：`{PAGE}_{PURPOSE}_{RESOLUTION}.png`，变体数字并入 PURPOSE，最多三个下划线
（如 `HOME_REWARD1_720P`）。禁止 `main_page_720p` 这类脱离消费模块语义的旧名称。

**common 契约**：以 `docs/AutoWSGR3.0/common/{system,device,vision}.md` 的公开出口为准；
能力不足时先按架构文档增加最小能力，不得引用 common 私有路径。

**dispatch 契约**：遵守 `[规范]dispatch-context临时规范.md`；导航器不创建自己的状态副本。

**命名下划线规则**：同文件内被其他 def 调用的辅助函数带 `_` 前缀；**跨文件**被调用的不带下划线
（例如 `stage_push/recognition.py` 的函数被同包 `checker.py` 调用，保持公开命名）。

**散落代码回收原则**：回收是**语义重写，不是文件搬运** —— 先读旧实现的调用方与边界，
再按新契约重写最小实现，禁止复制/移动/改名旧 `def`；旧实现只作只读参考。

## 12. 垂直切片交付规则

1. 盘点模板、ROI、分辨率、正负样本与目标事实；
2. 确认 common 公开能力，不足时提最小新增；
3. 在 dispatch Context 登记实际需要的字段与所有权；
4. 实现 checker 与必要的控制器跳转入口；
5. 注册一条路线并由执行器执行；
6. 每一步截图确认，最终目标页确认；
7. 补正常 / 失败 / 未识别 / 无路由 / 清理测试；
8. 更新本文档、架构文档与验证证据；
9. 验收通过后才允许业务调用方适配新入口。

## 13. 验收门禁

- checker 公共入口 import smoke；
- 模板资源存在、可加载、分辨率与 ROI 合法；
- 正样本命中、负样本拒绝、低置信度拒绝；
- 页面事实契约测试；
- Context 懒创建、字段所有权、任务隔离与关闭清理测试；
- 路由路径确定性与无路由失败测试；
- 控制器执行后逐步确认与最终确认测试；
- 导航异常、设备异常与业务恢复边界测试；
- 不引用 common 私有路径、不创建第二套 Context；
- `git diff --check` 与目标文件静态检查。

未完成实机验证的路线标记 `待验收`，不得标 `已完成`。
