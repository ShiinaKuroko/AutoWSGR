### 2.3 Dispatch 契约

导航器和 dispatch Context 同步建设，遵守：

`docs/features/[规范]dispatch-context临时规范.md`

当前规则：

- dispatch 是跨模块 Context 的唯一持有者；
- 任务先绑定作用域，第一次 `request()` 时懒创建 Context；
- 导航器不创建自己的状态副本；
- Context 字段必须有唯一写入者、读取者和生命周期；
- 每条业务链路必须把业务模块、dispatch 字段/API、联调和测试作为同一个垂直切片交付。

回收方式必须是语义重写，不是文件搬运：

1. 先读取散落定义的所有调用方、输入输出、副作用和错误边界；
2. 为新模块重新定义业务名称、公开入口、数据契约和依赖方向；
3. 在新模型中重写最小实现，禁止直接复制、移动、改名或机械粘贴旧 `def`；
4. 用新测试和真实链路验证新实现；
5. 旧实现只保留为只读参考，待新消费者全部迁移并完成删除验收后再移除。

任何“复制旧文件后再慢慢改”的提交都不视为完成回收。

## 3. 目标架构

目标目录：

```text
autowsgr/application/ui/navigation/
├── __init__.py          # 稳定出口
├── service.py           # 唯一公开入口 goto_page
├── route_registry.py    # 路径注册和 Controller 动作契约
├── route_calculator.py   # 只负责根据注册边计算路径
├── types.py              # PageName、Route、NavigationResult 等契约
└── page_checker/
    ├── __init__.py      # 内部 checker 包，不开放业务 checker
    ├── home.py           # 小型首页 checker：一个 check_home_page def
    └── <PAGE>.py         # 小型页面使用单文件；规模变大时再升级为子目录
```

依赖方向：

```text
业务层
  ↓ 目标页面
navigation.service
  ├── dispatch.context
  ├── page_checker
  ├── route_calculator
  ├── route_registry
  └── Controller action contract
       ↓
  UI Controller 页面跳转入口
       ↓
  common/device + common/vision
```

职责边界：

| 部分 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| `service.py` | 编排识别、同页短路、算路、执行、逐步确认和最终确认，返回导航结果 | 页面坐标、业务流程、恢复决策 |
| `page_checker/<PAGE>.py` | 小型页面中用一个 `def` 完成页面识别，只作为 Navigator 内部事实来源 | 路由计算、设备生命周期、error SL 执行、业务方直接调用 |
| `page_checker/<PAGE>/` | 只有页面 checker 复杂到单文件难以维护时才拆出的独立目录 | 预先创建空的 recognition/constants/workflow 文件 |
| `page_checker` | 维护内部 checker 分发，不向业务层暴露 checker | 具体页面识别和流程细节 |
| `route_registry.py` | 保存已确认边及其 Controller 动作契约 | 截图、页面识别、路径计算 |
| `route_calculator.py` | 根据当前页、目标页和注册边计算路径 | 截图、点击、Controller 实例化 |
| `dispatch.context` | 保存跨步骤导航事实 | 页面识别、重试、重启和业务决策 |
| UI Controller | 执行页面内部跳转动作和自身页面确认 | 维护全局路由图 |

### 3.1 唯一入口和内部职责

新导航器只提供一个公开入口：

```text
goto_page(ctx, target) -> NavigationResult
```

入口依次负责识别当前页面；如果当前页面已经是目标页面则直接返回确认结果；否则计算有序路径、调用
已注册的 UI Controller 动作、确认每一步和最终目标。
页面坐标、OCR、模板细节、业务流程、任务调度和恢复决策不属于导航器。

内部只保留两个执行职责：

| 私有职责 | 输入/输出 | 不负责 |
| --- | --- | --- |
| 当前页面 checker | `ctx -> current page fact` | 路由计算、Controller 动作 |
| 路径计算器 | `current + target -> route list` | 截图、点击、Controller 实例化 |
| service 执行阶段 | `ctx + route -> NavigationResult/异常` | 修改业务状态和恢复决策 |

路径记录至少包含 `source`、`target`、`controller`、`method` 和 `description`。路径判断器只读取页面关系，
调用器只消费已经选定的执行契约。

### 3.2 Page checker 边界

小型页面 checker 只保留一个 `def`，接收 dispatch `ContextHandle`，完成页面识别并返回 `bool`。
checker 通过 `ctx.runtime` 使用运行时服务，通过 ContextHandle 方法记录任务事实；不计算路由、不对业务层开放。

主页 checker 是 Navigator 内部的流程入口：

```text
check_home_page(ctx)
    ├── recognition_flow.capture_frame(ctx.runtime.ctrl, record_screenshot=ctx.record_screenshot)
    ├── HomePage(ctx.runtime).dismiss_current_overlay(navigation_context=ctx)
    └── recognition_flow.recognize_with_retry(...主页模板...) -> bool

浮窗识别和操作细节仍由 `HomePage.dismiss_current_overlay()` 持有；checker 负责编排调用顺序，主页模板重试
统一复用 `recognition_flow`。新 service 切片禁止业务层直接调用 checker。
```

当前 HOME checker 的参数和 ContextManager 仍处于迁移中；只有实现改为 `ContextHandle` 后，才算满足此契约。

主页浮层处理细节属于 `home/main_page`；HOME checker 调用该页面入口完成浮窗处理，再确认主页模板。
页面模板按实际消费模块归属，导航器只持有主页稳定页面模板。

## 10. 垂直切片交付规则

每条路线或 checker 链路必须按以下顺序推进：

1. 盘点页面模板、ROI、分辨率、正负样本和目标事实；
2. 确认 common 公开能力，不足时提出最小新增能力；
3. 在 dispatch Context 中登记实际需要的字段和所有权；
4. 实现 checker 和必要的 Controller 跳转入口；
5. 注册一条路线并由 executor 执行；
6. 每一步截图确认，最终目标页确认；
7. 补充正常、失败、未识别、无路由和清理测试；
8. 更新本台账、架构文档和验证证据；
9. 验收通过后，才允许业务调用方适配新入口。

## 11. 验收门禁

导航器每个垂直切片必须至少通过：

- checker 公共入口 import smoke；
- 模板资源存在、可加载、分辨率和 ROI 合法；
- 正样本命中、负样本拒绝、低置信度拒绝；
- `PageMatch` 或等价页面事实契约测试；
- Context 懒创建、字段所有权、任务隔离和关闭清理测试；
- 路由路径确定性和无路由失败测试；
- Controller 执行后逐步确认和最终确认测试；
- 导航异常、设备异常和业务恢复边界测试；
- 不引用 common 私有路径、不创建第二套 Context；
- `git diff --check` 和目标文件静态检查。

未完成实机或模拟器验证的路线必须标记为 `待验收`，不能标记为 `已完成`。
