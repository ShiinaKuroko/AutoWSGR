# 项目文件注释与代码编排规范

本规范适用于项目内所有手写源文件，重点约束 Python 模块的文件级
docstring、函数 docstring、注释和文件内代码编排。导航、页面控制器、业务模块
和通用能力模块均遵守同一套规则；生成文件不手工补充注释或调整结构。

本规范约束可读性、职责表达和维护顺序，不改变业务契约。与仓库
`pre-commit` 规则冲突时，以钩子实际要求为准。

## 文件级说明

每个 Python 模块必须在导入前写文件级 docstring。其他语言使用对应语言的顶层
注释，但字段和内容保持一致。文件级说明必须包含以下内容：

- `模块功能`：用一句话说明文件负责的业务能力。
- `上层调用`：列出直接调用方和调用目的。
- `下层依赖`：列出直接依赖的模块、组件或基础能力，以及依赖用途。

项目包路径从当前项目的顶层包开始书写，不重复 `autowsgr.` 前缀。例如使用
`application`、`business`、`common` 等作为路径起点。列表项统一使用 `-`，只写
直接调用方和直接依赖，不罗列传递依赖或无关历史背景。

推荐格式如下：

```python
"""模块功能：浴室页面内的识别、修理浮层操作和页面级返回。

上层调用：
- application.ui.navigation.graph.logistics：调用 go_back 完成浴室到后院的页面边动作。
- business.logistics.repair.bath_repair：调用浮层打开、舰船选择和修理结果读取方法。

下层依赖：
- application.ui.controller.bath_page.constants：提供浴室页面的坐标、颜色和时序。
- common.vision：提供页面与浮层识别。
- application.ui.controller.bath_page.recognition：完成卡片识别。

选择修理是浴室页面上的浮层，浮层打开时页面识别仍返回浴室。
页面控制器只负责浴室内部动作和返回动作，不负责跨页面寻路或修理任务调度。
"""
```

如果没有直接调用方或直接依赖，也要明确写出 `- 无`。文件级 docstring 应位于
模块首部，不要将它放在导入、常量或其他代码之后。

## 文件结构

按职责和功能组织文件内容：

1. 文件级说明。
2. 标准库、第三方库和项目内模块导入。
3. 顶层常量、类型、数据模型和注册表。
4. 对外功能入口，按业务功能分组。
5. 各功能入口使用的实现函数，紧邻对应入口。
6. 跨功能复用的私有函数和内部辅助逻辑。

同一功能的代码应尽量集中，避免在文件不同位置交替放置入口、校验、动作和
结果读取逻辑。导航图等声明式文件可以先声明业务拓扑，再定义拓扑使用的边动作，
但仍应保持每个功能组内部结构完整。

## Import 与私有对象规则

- 使用项目真实的规范包名、模块名和对象名；禁止使用 `as` 把包、模块、类或常量改成
  兼容名、缩写名或语义别名。
- `from` 可用于导入公开模块、类、函数和常量；如果目标是模块内的私有方法或私有常量，
  不得使用 `from module import _private_name`，必须导入所属模块，再通过模块名访问私有对象。
- 私有对象的调用必须保留其所属模块边界；不得通过导入别名、包级转出或复制实现伪装成公开 API。
- 需要兼容旧包名时，建立明确的兼容入口或适配模块；不得用导入别名代替兼容层。

## 配置归属与代码可发现性

维护者修改某个功能时，应先打开该功能对应的 Python 文件，在文件顶部的配置区域查找
本文件专属参数；不得要求维护者在无明确归属的全局文件中搜索。

- `page.py`：保存页面流程专属参数，例如 `sleep`、页面重试次数和流程阈值。
- `recognition.py`：保存 OCR 算法专属参数，例如置信度、采样次数和识别阈值。
- `constants.py`：保存模块跨文件共享值、静态业务数据，以及点击坐标、OCR 坐标、ROI
  和颜色等校准配置。

普通标量配置与校准配置必须在 `constants.py` 中使用不同的柱饰条分区；坐标、ROI 和颜色
不是普通标量常量，不得混入普通常量区，也不得在 `recognition.py` 或其他识别逻辑文件中
重新定义。页面或识别代码只消费 `constants.py` 的唯一配置，不复制同一参数。

每个 Python 文件的编排顺序固定为 `import`、`if TYPE_CHECKING`、日志模块引用、文件配置区、
`class`、公共/私有 `def`。配置区必须位于首个 `class` 或 `def` 之前，并使用业务含义明确
的柱饰条。这样可以方便快速修改代码配置、调试和实机调整；这是为了维护性和代码可读性
而允许的局部边界安排。类内部按业务流程在前、辅助方法在后的顺序组织。

同一语义的横纵坐标必须聚合，并按 `x`、`y`、`z` 轴顺序排列。配置区不得存放上下文、设备
对象、可变状态或调度规则；静态业务数据仍归 `constants.py`。

## 功能分组与函数顺序

- 文件首先按业务功能分组，再在功能组内按调用关系排列；不得为了全文件字母排序
  拆散一个完整业务流程。
- 同一功能使用统一前缀，并将相同前缀的函数放在一起。例如所有校验函数统一使用
  `check_*`，并集中放置；不要在同一语义下混用 `check_*`、拼写错误的前缀或无明确
  区别的其他命名。
- 一个功能组通常按“对外入口、状态检查、状态变更、结果读取、私有辅助函数”的
  顺序组织；实际顺序以业务调用链为准。
- 相关的 `open_*`、`select_*`、`read_*`、`go_back_*` 等函数应分别相邻，函数名应
  反映同一业务动作的统一前缀。
- 跨功能复用的辅助函数放在文件末尾或独立的通用模块中，不要复制到多个功能组。
- `__init__` 等 Python 特殊方法按类的常规写法保留在类首部。
- 函数顺序不得破坏 `pre-commit` 自动格式化结果。

## 空行与代码分区

- 连续空行最多保留两行；如果 `pre-commit` 有更严格的格式要求，以钩子结果为准。
- 使用短分区注释表示代码职责，例如：

```python
# ── 功能入口 ─────────────────────────────────────────────────
# ── 浴室页面检查 ─────────────────────────────────────────────
# ── 修理浮层操作 ─────────────────────────────────────────────
# ── 页面返回 ─────────────────────────────────────────────────
# ── 内部辅助 ─────────────────────────────────────────────────
```

- 分区名称使用业务含义，不使用只描述语法的标题。
- 分区注释只在文件确实包含多个清晰职责时使用；短文件不添加装饰性分区。

## 函数 docstring

函数和方法使用 Google 风格的精简 docstring。所有对外函数和有业务语义的内部
函数都必须说明入参和出参，并优先使用类型注解表达类型，使用 docstring 表达
业务含义。`self` 和 `cls` 不列入 `Args`。

推荐格式如下：

```python
def check_bathroom_page(screen: np.ndarray) -> PageMatch:
    """判断截图是否属于浴室页面，包括选择修理浮层状态。

    Args:
        screen: RGB 截图，形状为 (H, W, 3)。

    Returns:
        页面匹配结果；基础页面或选择修理浮层命中时视为匹配。
    """
```

编写规则如下：

- 首行概括函数的业务动作和结果，不重复函数名或逐行翻译代码。
- `Args` 说明每个入参的业务含义、格式和边界；`Returns` 说明出参的业务含义和
  关键状态，不只重复类型名。
- 没有显式入参或业务返回值时，按文档工具要求使用 `Args: None` 或 `Returns: None`，
  不让读者猜测函数契约。
- 有业务流程时，使用 `1、`、`2、`、`3、` 描述步骤和中断点；不把每一行实现
  机械地写进 docstring。
- 函数会主动抛出且调用方需要处理的异常使用 `Raises` 说明；生成器使用 `Yields`。
- 一行能完整说明且没有需要展开的契约时，可以使用单行 docstring，但仍应保留
  类型注解；对外函数和有业务语义的函数不得省略入参、出参说明。

## 注释原则

- 注释说明业务规则、设计原因、边界条件和兼容性约束，不重复代码本身。
- 注释应描述输入、动作、结果和失败条件中真正影响维护的部分。
- 不堆叠实现术语，不写与当前行为无关的历史背景。
- 临时 workaround 必须说明触发条件、移除条件和对应验证；不能只留下“临时处理”
  之类无法行动的说明。

## 依赖边界

- 文件级 `上层调用` 和 `下层依赖` 只描述直接关系，路径统一从当前项目顶层包开始。
- 上层模块通过下层模块公开的职责入口完成调用，不跨层访问内部状态或复制实现。
- 页面控制器负责页面内的点击、识别、等待和页面状态变更；导航器或业务服务负责
  跨页面寻路和任务调度，具体职责以项目现有架构为准。
- `common` 只提供无业务语义的设备、视觉、交互和校准能力；带明确业务或页面语义
  的聚合入口放在对应的 `application` 或 `business` 层。
- 仅被单个模块使用且带有该模块业务语义的实现保留在所属模块，不为了表面复用搬入
  通用层。

## 验证要求

每次治理至少执行与改动范围匹配的检查：

- 受影响功能的 focused pytest；纯文档或注释变更可说明无需运行业务测试。
- 受影响文件的 `pre-commit`。
- Python `compileall`、相关模块导入 smoke 和 `git diff --check`。

验证结果和无法执行的项目写入任务报告，不以未运行的检查宣称通过。
