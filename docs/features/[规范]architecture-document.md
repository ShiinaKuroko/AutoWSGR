# 架构文档编写规范

状态：生效

适用范围：各代码模块目录下的 `<模块名>.md` 模块架构说明文档。

本规范以 `common/system.md` 为结构基准，抽象出所有模块架构文档必须遵守
的内容、顺序和验收要求。模块的具体业务语义由各模块文档填写，本规范不替代模块
专项规范。

## 0. 规则继承和文档边界

架构文档涉及 Python 代码、模块出口、配置、错误和测试时，继承：

- 项目根目录 `AGENTS.md`；
- `[规范]python-code-style.md` 的全部通用 Python 规则；
- 目标模块的专项规范；
- 本架构文档规范。

同一优先级的规范发生冲突时，必须暂停编写并报告冲突。

架构文档描述当前已经实现、已经验证或明确批准的模块契约，不用于承载：

- 尚未批准的重写方案；
- 未实现的未来设计；
- 阶段性工作过程和每日进度；
- 只适用于一次迁移的临时命令；
- 与模块无关的全局架构讨论。

未实现的设计放入 `docs/features/[todo]*` 或任务书。实现完成并验证后，才回写
架构文档。

## 1. 文件命名和元数据

### 1.1 文件位置和命名

架构文档统一放在 `docs/AutoWSGR3.0/` 下，**目录层级与代码一一对应**：顶层按四个业务域分
`common/`、`dispatch/`、`application/`、`business/`，往下逐级复制模块的代码路径。

文档放在被描述模块的**父目录**，文件名 `<模块名>.md`。

```text
docs/AutoWSGR3.0/common/system.md                                        # 描述 autowsgr/common/system/
docs/AutoWSGR3.0/common/vision.md                                        # 描述 autowsgr/common/vision/
docs/AutoWSGR3.0/application/ui/controller/home/main_page.md              # 描述 .../controller/home/main_page/
docs/AutoWSGR3.0/application/ui/controller/operations/sortie_page/main_page.md
docs/AutoWSGR3.0/application/ui/navigation/checker/event.md
```

`<模块名>` 必须与代码目录名一致，不使用宽泛的 `common`、`core`、`utils` 或 `manager`
作为唯一名称；同一父目录下多个模块的文档靠文件名区分。

示例：

```text
docs/AutoWSGR3.0/common/system.md
docs/AutoWSGR3.0/common/device.md
docs/AutoWSGR3.0/dispatch/context/context.md
```

### 1.2 文件开头

文档开头必须包含标题和最小元数据：

```markdown
# <module> 架构说明

版本：AutoWSGR-3.0 第 X 版
状态：草案 / 生效 / 暂停 / 废弃
适用范围：<代码目录或模块入口>
实现基线：<对应分支、提交或确认日期>
```

`状态` 为 `生效` 时，文档内容必须与当前代码和测试保持一致。`草案` 不得作为
生产调用契约被其他模块直接引用。

### 1.3 文档树与代码树对齐

架构文档是一棵树，与代码目录树一一对应：**一个代码单元对应一份文档**。

| 代码单元 | 文档位置 | 文档名 |
| --- | --- | --- |
| 包目录 `A/B/` | `docs/AutoWSGR3.0/…/A/` | `B.md` |
| 模块文件 `A/C.py` | `docs/AutoWSGR3.0/…/A/` | `C.md` |

以下代码单元**不单独建文档**，写进所属包目录的文档：

- `__init__.py`：只做导出，写进父文档的「公开出口」；
- 纯数据文件：`types.py`、`constants.py`、`errors.py`、`models.py`、`config.py`
  这类只有声明、没有编排的文件，写进父文档的「文件职责表」。

**父文档必须完整列出它的全部直接子项**（直接子目录 + 直接文件），一项一行：

| 子项 | 类型 | 文档 | 职责 |
| --- | --- | --- | --- |
| `registry.py` | 文件 | [registry](<./registry.md>) | 页面确认与可达边注册 |
| `service.py` | 文件 | [service](<./service.md>) | 算路、浮窗与启动段 |
| `types.py` | 数据文件 | 本文件「文件职责表」 | 页面名与导航错误 |
| `checker/` | 子目录 | [checker](<./checker.md>) | 各页面识别 |

漏项即视为文档缺陷，不允许用“其他文件略”代替。

### 1.4 层级引用规则

架构文档之间通过引用组成可跳转的知识库，替代把细节堆在一份文档里：

1. **只引架构文档**：只能链接 `docs/AutoWSGR3.0/` 下的 `*.md`。
   不引用任务书、todo、知识、台账、计划、评审、已完成等过程性文档；需要其中的结论时，
   把结论写进本模块文档，而不是转引。
2. **只引直接关系**：父文档只引用直接子项；模块之间只引用直接协作方。不跳级引用
   （`navigation` 不直接链到 `stage_push`），不列完整依赖树。
3. **引用方向与代码依赖方向一致**：下层文档不引用上层。
4. **必须给可点击链接**，不用“见 xxx 文档”这类纯文字表述。
5. **链接路径统一用尖括号包住**：`[registry](<./registry.md>)`。路径里出现空格、
   方括号等特殊字符时这是唯一能正确解析的写法，统一这么写省得记。
6. **必引场景**：
   - 本模块用到的下层能力 → 引下层架构文档的对应能力章节；
   - 本模块注册进的框架（注册表、工厂、钩子）→ 引该框架的架构文档；
   - 本模块入口的调用方 → 引上层架构文档。
7. **禁止**：死链、跨级引用、循环引用描述同一契约、用引用代替本层契约。引用只是补充，
   本层的业务契约必须在本层写全。

### 1.5 顶层索引

`docs/AutoWSGR3.0/README.md` 是整个架构知识库的入口，只负责导航，不写实现细节：

1. 分层架构图，标明各层名称和职责；
2. 层级索引表：`层 | 包路径 | 职责 | 模块文档`，每个模块一个链接；
3. 各业务域的模块清单，每项一个链接；
4. 与模块文档遵守同一套层级引用规则：它只链接自己的直接子项。

## 2. 固定章节顺序

模块架构文档必须按以下顺序组织。某个章节对目标模块确实不适用时，保留章节并
明确写 `不适用` 及原因，不得静默删除导致不同模块的文档结构失去可比性。

```text
1. 模块定位
2. 模块架构
3. 能力总览
4. <能力 A>
5. <能力 B>
...
N. 统一配置
N+1. 错误约定
N+2. 日志约定
N+3. 公开出口和调用边界
N+4. 模块维护方法
N+5. 验收门禁
```

能力章节的数量按模块实际提供的公开能力决定。每个公开能力必须有独立章节，
不能只在总览表中列出名称而不说明契约。

## 3. 模块定位

使用 `## 1. 模块定位`，必须回答以下问题：

1. 模块在项目分层中的位置是什么；
2. 模块解决的业务问题是什么；
3. 模块对外提供什么能力；
4. 模块明确不负责什么；
5. 模块的状态、配置、资源和错误由谁拥有；
6. 模块与上层、同层、下层的关系是什么。

推荐写法：

```markdown
<module> 是 <分层> 的 <业务基础/流程编排/运行时支撑> 模块。
它只负责 <能力列表>，不负责 <排除项>。
模块的 <状态/配置/资源/错误> 由 <唯一所有者> 持有。
```

公共层不需要为了完整性罗列所有上层调用者；只有调用关系影响契约、所有权或
依赖方向时，才在本节说明。

## 4. 模块架构

使用 `## 2. 模块架构`，至少包含目录树、文件职责、依赖方向和出口策略。

### 4.1 目录树

目录树必须来自当前代码，不得绘制尚未创建的未来目录。每个实际文件后面写一句
职责说明。

目录树**只画到直接子项**：子目录本身列出并标注职责，不再展开它的内部文件；
内部展开由该子目录自己的文档负责（见 1.3、1.4）。可点击的文档链接放在 4.2
的文件职责表里。

```text
autowsgr/<layer>/<module>/
├── __init__.py       # 稳定公共出口
├── config.py         # 模块配置和默认值
├── constants.py      # 静态业务常量
├── service.py        # 对外主入口
└── internal.py       # 私有实现
```

如果文档描述的是增量重写中的目录，必须显式标注 `目标结构`，不能伪装成当前
实现结构。

### 4.2 文件职责表

目录树之后必须给出文件职责表，**覆盖全部直接子项**；有独立文档的子项给出链接，
没有独立文档的（`__init__.py`、纯数据文件）在表内说明职责：

| 文件/目录 | 文档 | 负责内容 | 不负责内容 |
| --- | --- | --- | --- |
| `__init__.py` | 本表说明 | 稳定出口 | 业务实现和隐式初始化 |
| `<file>.py` | [<file>](<./<file>.md>) | <明确职责> | <明确排除项> |
| `<subdir>/` | [<subdir>](<./<subdir>.md>) | <子模块职责> | <明确排除项> |

每个运行时状态只能有一个文件或对象作为权威所有者。文档必须指出这个所有者。

### 4.3 依赖方向

必须用文字、表格或图示表达依赖方向：

```text
上层调用者
    ↓
模块公开入口
    ↓
模块内部编排
    ↓
基础能力 / system / 第三方库
```

必须同时列出禁止方向。例如：

- `common` 不依赖 `application` 或 `business`；
- 基础引擎不依赖页面流程；
- 识别模块不反向调用导航器；
- 配置模型不持有运行时状态；
- `__init__.py` 不复制或包装内部实现。

### 4.4 出口策略

说明哪些对象是稳定公共出口，哪些只是内部实现。公共出口必须与代码中的
`__init__.py`、`__all__` 或明确导入路径一致。

## 5. 能力总览

使用 `## 3. 能力总览`，用表格列出模块的全部稳定能力：

| 能力 | 对外入口 | 所在文件 | 输入 | 输出/副作用 | 负责内容 | 不负责内容 |
| --- | --- | --- | --- | --- | --- | --- |
| <能力名> | `<module>.<name>` | `<path>` | <类型和语义> | <返回值/状态变化> | <职责> | <边界> |

表格中的入口、类型、返回值和副作用必须能在代码中找到对应实现。不存在稳定
入口的私有函数不得作为模块能力列出。

## 6. 能力契约章节

每项能力使用一个 `## <编号>. <能力名>` 章节，至少包含以下内容。

### 6.1 能力说明

解释业务语义、解决的问题和适用条件，不要逐行翻译代码。

### 6.2 稳定入口

写出完整导入路径、签名和调用约束：

```text
<module>.<entry>(<parameters>) -> <return type>
```

必须说明：

- 必填和可选参数；
- 参数类型、单位、范围和空值含义；
- 返回值的业务语义；
- 是否修改上下文、文件、设备或其他外部状态；
- 调用前置条件；
- 成功、失败和不确定结果的区别。

### 6.3 调用示例

示例必须使用真实公共入口，不能调用私有函数、测试替身或不存在的兼容别名。
示例应覆盖最小成功调用：

```python
from autowsgr.<layer> import <module>

result = <module>.<entry>(<valid arguments>)
```

如果入口会失败，必须再给出失败边界或异常示例。

### 6.4 错误和副作用

用表格说明边界：

| 场景 | 行为 | 异常/结果 | 处理者 |
| --- | --- | --- | --- |
| <输入非法> | <拒绝/规范化> | `<Error>` | <调用层> |
| <资源不可用> | <失败> | `<Error>` | <恢复层> |
| <可预期分支> | <返回结果> | `<Result>` | <业务层> |

模块只记录或返回事实，不在没有契约的情况下吞掉异常、静默降级或替调用方做
恢复决策。

### 6.5 维护规则

说明如何扩展此能力、哪些代码可以复用、哪些内容必须留在上层，以及新增入口
需要同步修改哪些文档和测试。

## 7. 配置约定

模块存在配置时使用 `## 统一配置`；不存在时写明 `本模块无运行时配置`。

配置章节必须说明：

1. 配置模型所在位置；
2. 字段命名和模块前缀；
3. 默认值、类型、单位和作用；
4. 是否允许用户或 GUI 覆写；
5. 覆写入口和生效时机；
6. 配置模型不负责的运行时行为。

字段表使用以下形式：

| 字段 | 默认值 | 类型/单位 | 业务作用 | 是否可覆写 | 生效时机 |
| --- | --- | --- | --- | --- | --- |
| `<PREFIX_NAME>` | `<value>` | `<type>` | <meaning> | 是/否 | <when> |

只有会被用户、GUI 或运行部署改变的值才增加配置。固定坐标、模板路径、算法常量、
一次性流程参数和预留扩展字段不得伪装成配置。

## 8. 错误约定

模块存在专用错误时使用 `## 错误约定`，至少说明：

- 错误基类和继承关系；
- 哪一层定义基础错误，哪一层定义具体业务错误；
- 哪些异常允许被捕获；
- 哪些异常必须继续向上抛出；
- 恢复、重试、停止和人工处理分别由谁决定。

推荐使用错误树和维护表：

```text
<BaseError>
├── <DomainError>
└── <OperationError>
```

| 错误 | 定义位置 | 触发条件 | 处理者 | 是否可重试 |
| --- | --- | --- | --- | --- |
| `<Error>` | `<module>` | <condition> | <owner> | 是/否/由上层决定 |

## 9. 日志约定

模块使用日志时，必须说明：

- 日志对象的获取入口；
- channel 命名；
- `debug`、`info`、`warning`、`error` 各自记录什么；
- 哪些日志是业务结果，哪些只是诊断信息；
- 关键日志的格式和字段；
- 是否允许记录截图、路径、设备信息或用户数据。

`info` 日志必须能表达已发生的业务动作或结果；轮询、分支尝试和中间匹配详情
放在 `debug`；可预期但未完成的结果使用 `warning`；异常终止或契约失败使用
`error`。具体格式继承项目日志规范。

## 10. 公开出口和调用边界

使用 `## 公开出口和调用边界`，分成稳定出口和内部内容两部分。

### 10.1 稳定出口

列出可以被其他模块引用的完整路径、签名和用途：

| 出口 | 来源 | 调用者可以做什么 | 调用者不能做什么 |
| --- | --- | --- | --- |
| `<module>.<entry>` | `<file>` | <allowed> | <forbidden> |

### 10.2 内部内容

列出不得跨模块调用的内容，包括私有函数、缓存、内部状态、构造辅助函数和
实现细节。测试直接调用私有函数不能使其变成生产公共出口。

本节必须与 `__init__.py`、`__all__`、实际 import 路径和调用方保持一致。文档
不得把旧接口、兼容别名或测试入口写成新架构稳定出口。

## 11. 模块维护方法

使用 `## 模块维护方法`，至少覆盖以下场景。

### 11.1 添加能力

1. 确认能力属于本模块，而不是上层业务或下层基础设施；
2. 在现有文件职责内实现，只有真实职责增长时才拆新文件；
3. 定义稳定入口、输入输出、异常和所有权；
4. 更新能力总览和对应能力章节；
5. 更新公共出口、单测和调用示例；
6. 执行本模块验收门禁。

### 11.2 添加文件格式、资源或子模块

说明新增文件的归属、允许的依赖、路径安全边界、加载/保存契约和测试位置。
不得为了“以后可能需要”创建空目录、空接口或兼容包装层。

### 11.3 修改配置

记录字段变化、默认值变化、用户覆写方式、校验变化、生效时机和受影响调用者。
配置变更必须同步修改字段表、示例和失败路径测试。

### 11.4 修改公开契约

记录旧契约、新契约、迁移范围、删除时间和验证结果。不能只改文档而不改实现，
也不能只改实现而让架构文档继续描述旧行为。

### 11.5 删减能力或文件

1. grep 确认没有调用方，包含测试、工具和文档引用；
2. 删除实现，不留兼容壳、旧名别名或转发层；
3. 删除能力章节、能力总览行和公开出口行；
4. 修正父文档与协作方文档里指向它的链接；
5. 删除对应测试和调用示例；
6. 执行本模块验收门禁。

删减与新增一样必须在同一批里回写文档，不允许代码已删而文档仍挂着。

### 11.6 参数传入与穿透规则

必须说明本模块入口的参数从哪里来、怎么往下传：

- **调用方传入**：参数由直接调用方给定，本模块只负责校验和使用；
- **框架透传**：参数经框架原样传递，例如 `**params` 从入口一路传到边的 `action`；
  必须写明透传链路和可用键；
- **内部计算**：参数由本模块自己算出，调用方不提供，例如由数据表定位出的坐标。

还必须写明：

- 哪些参数禁止由调用方预先算好再传（应在本模块内部现算，避免把下层能力暴露给调用方）；
- 缺省值、必填项、类型和取值范围；
- 参数非法时的失败行为：抛错、拒绝还是兜底。

### 11.7 框架注册

本模块参与注册表、工厂或钩子时，必须说明：

1. 参与哪些注册点，例如页面名表、确认表、可达表；
2. 新增一个注册项的完整步骤：改哪几个文件、什么顺序、必须同步导出到哪里；
3. 每个注册项的必填字段、可选项和校验；
4. 注册冲突、重复注册和注册失败时的表现；
5. 删除一个注册项的步骤。

注册点自身的定义、数据形状和校验属于框架文档；本模块只写“我怎么注册”。

## 12. 验收门禁

每个架构模块交付前必须根据实际能力选择并记录以下检查：

```text
1. 公共入口 import smoke
2. 目标源码 compile / 静态检查
3. 模块专属 pytest
4. 默认配置、合法配置和非法配置路径
5. 关键成功、失败和边界行为
6. 错误归属和恢复边界
7. 路径、权限、原子写入或设备安全边界（适用时）
8. 日志级别、格式和敏感信息检查（适用时）
9. 文档示例可以对应当前实现
10. 文档树与代码树对齐：每个代码单元都有归属（自己的文档或父文档的说明）
11. 父文档引用了全部直接子项，没有漏项
12. 引用无死链、无跨级引用、无过程性文档链接
13. `git diff --check`
```

无法执行的检查必须在文档或交付说明中列出原因和剩余风险，不得把未验证的
能力写成“已支持”。

架构文档的验收重点是契约一致性：目录、出口、签名、配置、异常、日志、测试路径
和实际代码必须互相对应。

## 14. 文档与代码同步

架构文档是上层调用的入口，不是事后总结。**代码改动必须与文档改动同批完成**，
不允许"先改代码、文档以后补"。

以下改动必须在同一批里回写对应章节：

| 代码改动 | 必须同步的文档位置 |
| --- | --- |
| 新增、删除、改名公开入口 | 能力总览 + 对应能力章节 + 公开出口 |
| 改函数签名、返回值或失败边界 | 对应能力章节的稳定入口 + 错误和副作用 |
| 新增、删除、移动文件或目录 | 目录树 + 文件职责表 |
| 改依赖方向或跨层调用 | 依赖方向 + 禁止方向 |
| 改配置字段、默认值或覆写方式 | 统一配置 + 字段表 |
| 改错误类型或归属 | 错误约定 |
| 改日志通道、级别或字段 | 日志约定 |
| 改模板、坐标、数据等资源路径 | 能力章节 + 资源说明 |
| 新增活动、页面或玩法分支 | 能力总览新增独立章节，不能只加一行 |

每份文档的 `实现基线` 必须写清对应的提交或确认日期；改动公开面后必须更新它，
让读者能判断文档描述的是哪一版实现。

文档与代码不一致时，以代码为准，并在同批修正文档；不得让文档继续描述旧行为。

## 15. 与 Code Graph 的对齐（建议，非门禁）

`tools/code_graph` 能静态产出模块、定义、导入和调用关系。它**不强制维护**，
agent 需要核对事实或做重构比对时再用；不用它也不影响交付。

有价值的使用场景：

| 架构文档内容 | 可用手段 |
| --- | --- |
| 目录树、文件职责 | `python tools/code_graph/code_graph.py build` 的节点 |
| 依赖方向、禁止方向 | `python tools/code_graph/code_graph.py check` 的层级违规 |
| 公开出口、内部内容 | `python tools/code_graph/code_graph.py explain <模块>` |
| 重构前后契约是否变化 | `python tools/code_graph/code_graph.py diff <旧图> <新图>` |

Code Graph 是核对工具，不是文档来源：文档内容必须能对应真实代码，不能只把图谱
产物贴进文档。
