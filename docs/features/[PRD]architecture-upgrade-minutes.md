## 2026-08-29：任务模型与交互链路

### 一、Sakuya 工作模式

- Sakuya 是长期替代实现分支，不是逐文件兼容迁移分支。
- 中间阶段允许破坏、删除和重写旧 Kuroko 框架，不要求每个中间提交都能运行旧功能。
- 每次完成一个可运行的垂直功能切片，再开始下一个切片。
- 开发期间使用短 smoke、导入/编译检查和模拟器主链路验证；功能接受后补核心单测，完整 pytest/lint 作为里程碑门禁。
- Sakuya 架构升级分支的 `AGENTS.md` 是分支本地规则，严禁同步到 `ShiinaSakuya`、`ShiinaKuroko`、`main` 或发布/PR 分支。

### 二、GUI 与后端交互链路

1. GUI 编辑 YAML 并保存到本地。
2. GUI 加载 YAML 只属于 GUI 域内操作，不立即发送完整 YAML 到后端。
3. GUI 启动任务时，通过 HTTP 发送任务类型、YAML 位置和必要的额外字段。
4. 后端收到信号后，根据允许的 YAML 根目录解析任务定义；HTTP 不传输整份 YAML。
5. 后端将 YAML 任务定义转换为运行时任务实例，进入调度和执行。
6. 更高优先级任务到达时，调度器在当前任务最近的安全停止节点暂停当前任务，先执行高优先级任务，再恢复原任务。
7. 原任务恢复时保留原任务实例的进度和暂停点，不创建一个全新的逻辑任务。
8. 任务完成后，根据下一个任务的入口要求选择最小导航回退：同任务同舰队可回到舰队编辑页；不同普通出征任务回到章节导航；需要首页起步的任务回到首页。
9. 未分类异常进入 `failed`，必须保留原始错误；清理/回主页失败作为附加错误，不得覆盖根因。
10. 用户取消通过 HTTP 发送停止请求；后端在最近安全停止节点执行停止流程，导航器将游戏恢复到首页初始态，任务最终标记为 `cancelled`。

### 三、YAML 定义与运行时任务状态的区分

YAML 的执行情况不是 YAML 文件自身的状态。必须拆成三个概念：

#### 1. `TaskDefinition`

- 来源：GUI 提供的 YAML 路径和后端读取到的 YAML 内容。
- 性质：加载后只读的任务定义快照。
- 内容：任务类型、计划参数、舰队、次数、停止条件、业务配置等。
- YAML 文件在任务运行期间被修改时，不影响已经入队的快照；后续任务可重新加载新版本。

#### 2. `TaskInstance`

- 来源：一次 GUI 启动请求创建的逻辑任务。
- 标识：唯一 `task_id`。
- 内容：`TaskDefinition` 引用/摘要、优先级、当前状态、业务进度、当前步骤、安全暂停点、取消原因、结果和错误。
- 暂停和恢复始终属于同一个 `TaskInstance`，不能通过重新读取 YAML 把进度重置。

#### 3. `ExecutionAttempt`

- 含义：同一个逻辑任务的一次实际执行尝试。
- 普通完成可能只有一次；被高优先级任务暂停后，会产生下一次 attempt。
- attempt 是调试和日志边界，不是 GUI 看到的新的任务。

### 四、Processor 在链路中的位置

Processor 位于 HTTP/CLI 输入适配之后、具体业务 Executor 之前：

```text
HTTP / CLI / Timer
        ↓
server adapter：解析最小请求信号
        ↓
Processor：校验、创建 TaskInstance、排队/暂停/恢复/取消决策
        ↓
TaskDefinitionLoader：按允许根目录加载 YAML 快照
        ↓
Executor：执行具体业务步骤
        ↓
Navigator / Device / OCR 等 infra 能力
        ↓
TaskEvent / TaskResult → server WebSocket/HTTP
```

Processor 不负责实现战斗、导航或 YAML 业务解析。它可以要求定义加载器在准入阶段验证并冻结 YAML 快照，但“如何执行任务”仍属于 Executor。

Processor 必须负责：

- 是否接受、排队或拒绝任务；
- 当前任务是否允许被暂停；
- 哪个任务优先执行；
- 任务状态转换；
- 取消请求的协调；
- 恢复原任务和选择下一个任务的过渡策略；
- 发布任务生命周期事件。

### 五、优先级规则

- 延续原有业务优先级关系，但统一限定在 `0..10` 范围内。
- 约定数字越小优先级越高，保持原有远征、奖励、战役、演习、常规战、浴室修理的相对关系。
- 优先级默认由任务类型/业务画像决定，不由 GUI 任意填写；额外字段只能在明确的调度契约中覆盖。
- 该规则必须只在一个调度模型中实现，不能让 Processor 与旧 Scheduler 使用相反排序。

当前业务优先级（从高到低）确定为：

```text
远征 > 奖励 > 战役 > 演习 > 决战 > 普通出征 = 活动出征 > 其他
```

- 优先级只用于战斗相关任务和插队判断，不作为所有业务属性的通用排序。
- 普通出征与活动出征同级；同级任务不互相抢占，按入队顺序等待。
- “其他”任务为最低优先级，不能抢占上述任务。
- 建议映射为 `0..6`：远征 `0`、奖励 `1`、战役 `2`、演习 `3`、决战 `4`、普通/活动出征 `5`、其他 `6`；保留 `7..10` 供后续业务扩展。

### 六、资源与状态所有权

“谁持有”指哪个对象是某项资源或状态唯一允许创建、替换和写入的权威所有者，其他模块只能通过它提供的接口读取或请求变更。

| 对象 | 唯一所有者 | 其他层的用法 |
|---|---|---|
| YAML 任务定义 | `TaskDefinitionLoader` / Plan repository | 读取不可变快照 |
| 当前任务队列与状态 | `Processor` / Runtime | 提交命令、订阅事件 |
| 设备连接、OCR、基础服务生命周期 | `RuntimeSession` | Executor 使用窄接口 |
| 设备 lease | Runtime/Processor 的调度边界 | infra 只执行已获准的操作 |
| 业务进度 | 当前 `TaskInstance` | Executor 更新定义好的进度事件 |
| 页面导航状态 | Navigator | Executor 请求到达某个页面或安全锚点 |
| 舰队/远征等业务状态 | 对应 Domain state owner | 页面层提供观测结果，不复制第二份可写状态 |
| GUI 编辑中的 YAML | GUI 本地存储 | 后端只在任务准入时读取快照 |

`GameContext` 不应继续作为上述所有状态的共同写入口。后续应逐步拆成 RuntimeSession、TaskInstance 和各领域状态。

### 七、任务事件责任

Processor 发布所有任务生命周期事件：

```text
accepted → queued → running → paused → resumed → stopping
                                      ↓
                         completed / failed / cancelled
```

Executor 可以报告领域进度事件，例如 `rival_done`、`node_changed` 或 `loot_found`，但不能自行改变任务生命周期或决定外部任务抢占。Processor 接收这些事件并进行状态转换，再由 server 转发给 GUI。

日志、OCR 明细和业务诊断不需要全部经过 Processor；只有 GUI 依赖的任务状态和进度事件必须走统一任务事件通道。

### 八、完成、暂停、取消和异常

- **暂停**：调度器发出 pause 请求；Executor 在最近安全节点停止，保留 `TaskInstance.progress`，回到可交接锚点后报告 `paused`。
- **恢复**：Processor 重新调度同一个 `TaskInstance`，从任务定义的安全起点和已保存进度继续；不是重新创建任务。
- **完成**：Executor 报告业务完成，Processor 根据后继任务入口要求选择最小过渡导航，之后标记 `completed`。
- **取消**：用户请求是控制意图，不立即强杀线程；在安全节点完成停止、回首页，再标记 `cancelled`。
- **异常**：业务或基础设施异常标记 `failed`，保留根因、当前步骤和清理结果；不得把异常伪装成取消或成功。
- **不可打断原子段**：战斗动画、结算点击等不可安全回退的阶段只能延迟暂停/取消请求。

### 九、内部契约与验证策略

- Sakuya 先统一后端内部的 `TaskStatus`、`ControlIntent`、`Command`、`TaskEvent` 和 `TaskResult`，不为当前 GUI/后端旧契约保留中间兼容形态。
- GUI 与后端的最终契约适配放在新架构功能完成、准备替换 Kuroko 的集成阶段统一处理。
- 架构开发和功能调试以 `tools/e2e` 的真实业务链路为主；不要求每次迭代运行完整 pytest 或 GUI 测试套件。
- 每个垂直功能验收后，再补充核心状态、调度、错误和序列化单测，作为后续回归基础。
- E2E 验证必须覆盖任务终态、暂停/恢复、取消、异常清理和主页/交接锚点，不能只验证主路径成功。

## 2026-08-29：战斗域与导航交接

### 一、实现层所有权

- 用户只负责宏观业务语义和必要的细节把控。
- 具体代码分层、状态所有者、接口形态、生命周期和实现取舍由 Agent 根据本纪要、现有业务和验证结果自行决定。
- 若实现选择会改变用户可见业务规则、任务含义或最终 GUI 契约，必须在实施前单独说明并请求确认。

### 二、战斗域功能入口

战斗域包含五类功能：

- 普通出征：入口在出征页面。
- 活动出征：入口在首页。
- 演习：入口在出征页面。
- 战役：入口在出征页面。
- 决战：入口在出征页面。

出征页面还可以进入远征页面；远征属于后勤域，但共享出征页面的导航基础设施。

### 三、导航交接原则

- 每类任务的入口页面和当前页面之间的最短导航路径应可追溯。
- 任务完成或暂停时，导航器应能根据下一个任务的入口要求计算最短回退/交接路径。
- “回退”不应被实现为固定返回首页；在安全且可复用的情况下，应保留章节、面板或舰队编辑上下文。
- 需要首页起步的任务仍必须回到首页初始态；不可复用的上下文不得跨任务保留。

## 下一层：dispatch

下一轮讨论范围为 `dispatch` 的业务职责：任务准入、排队、优先级、暂停/恢复、取消和任务交接；不讨论具体 Python 类或文件实现。

### dispatch 最小状态机提案（待确认）

#### 一、任务生命周期

对外稳定状态保持少量且可解释：

```text
accepted -> queued -> running -> completed
                         |  \-> failed
                         |  \-> stopping -> cancelled
                         \-> paused -> queued -> running
```

- `accepted` 只表示请求已通过准入校验；进入等待后变为 `queued`。
- `running` 期间只允许一个任务持有设备执行权；同一 `TaskInstance` 可经历多次
  `running -> paused -> running`，每次恢复递增 `ExecutionAttempt`，不改变 `task_id`。
- 连续任务的单轮完成只更新进度并执行下一轮所需的最小导航，不产生 `completed`；
  最后一轮及其交接导航成功后才进入 `completed`。
- 业务执行完成后，调度器先等待导航器确认目标锚点稳定，再发布终态；导航失败仍是
  `failed`，但要保留“业务已完成”和导航错误两个结果字段。
- 队列中的任务取消可直接进入 `cancelled`；运行中或暂停中的取消必须经过安全停止、
  清理和回首页流程后才能进入 `cancelled`。
- 异常终态保留根因、发生步骤和清理结果；清理错误不得覆盖根因。

#### 二、调度选择

- 优先级数字越小越高，严格限制为 `0..10`；当前映射为：远征 `0`、奖励 `1`、
  战役 `2`、演习 `3`、决战 `4`、普通/活动出征 `5`、其他 `6`。
- 只有新任务优先级**严格高于**当前任务时才申请抢占；同级任务不抢占，按稳定入队
  顺序执行。不得在抢占时修改任务本身的业务优先级。
- 抢占任务必须先进入 `paused` 并保存同一个 `TaskInstance` 的进度和安全锚点；高优先
  任务结束后，原任务恢复。若此时另有更高优先级任务就绪，继续按同一规则处理；同级
  情况优先恢复被打断任务，避免无界饥饿。
- 当前任务处于不可打断原子段时，新任务先排队，等执行器到达安全节点再切换；不强杀
  线程，也不复制一份任务。

#### 三、职责边界

```text
server adapter -> Command -> Processor -> Executor
                                      -> Navigator / RuntimeSession
                              <- TaskEvent / TaskResult
```

- `Processor` 是任务实例、队列、优先级、控制意图和生命周期事件的唯一写入者。
- `Executor` 只负责领域步骤，报告进度、检查点和结果；不能自行抢占或改变生命周期。
- `Navigator` 负责到达安全锚点和任务交接页面；`RuntimeSession` 负责设备/OCR/基础
  服务与 lease。二者不保存第二份任务状态。
- HTTP/CLI/定时器只创建内部 `Command`；GUI 适配留在最终集成阶段。

#### 四、首批 E2E 验收场景

1. 普通提交：准入、排队、执行、最小交接后 `completed`。
2. 高优先级抢占：低优先级任务保持同一 `task_id` 和进度，暂停后恢复。
3. 同级任务：不抢占，按入队顺序执行。
4. 队列取消和运行中取消：都回首页并进入 `cancelled`。
5. 业务异常和清理异常：进入 `failed`，根因与清理结果均可见。
6. 连续任务：轮次间保持同一实例，只在最终轮完成后结束。

## 下一层：business

### business 层收口提案（待确认）

#### 一、定位

`business` 是面向游戏业务能力的用例编排层，接收已校验的任务定义，调用运行时
能力完成一条完整业务链，并返回领域结果、进度和安全检查点。

```text
Command -> Processor -> BusinessExecutor -> RuntimeSession / Navigator / CombatEngine
                                      <- DomainProgress / Checkpoint / BusinessResult
```

业务层应包含普通出征、活动出征、演习、战役、决战、远征检查、奖励领取等可被
调度的用例，以及供这些用例直接组合的补给、修理、编队等内部业务操作。

#### 二、必须负责

- 将一个业务用例编排为可验证的步骤序列，并声明入口锚点、可暂停检查点和终态锚点。
- 使用领域策略和规则，例如 `FleetPolicy`、地图节点决策、舰损/修理条件和连续轮次。
- 在每个安全检查点报告语义进度；暂停恢复时依据 `TaskInstance` 的检查点和游戏
  实际状态继续，不重新创建逻辑任务。
- 对不可逆操作等待结果确认；业务错误向上抛出并保留发生步骤，不把失败吞成空结果。
- 返回领域结果，不直接生成 HTTP/WS DTO，不改变任务生命周期状态。

#### 三、明确不负责

- 不负责队列、优先级、抢占、取消决策或 `TaskStatus` 写入；这些归 `Processor`。
- 不负责 HTTP、WebSocket、GUI 字段和旧 `ops` 兼容入口。
- 不直接实现截图、OCR、坐标点击、页面识别、设备连接或 lease；这些由
  `RuntimeSession`/`Navigator`/infra 提供语义能力。
- 不读取裸 YAML 路径或自行解析外部请求；只接收 `TaskDefinition` 已生成的类型化参数。
- 不通过全局 `GameContext` 保存跨任务可写业务状态；任务进度归 `TaskInstance`，
  领域状态归对应 owner。

#### 四、用例与内部操作的区别

- **可调度用例**：演习、普通/活动出征、战役、决战、远征检查、奖励领取。
- **内部业务操作**：初始化前置、导航到锚点、补给、澡堂修理、编队、收取动作和
  战斗引擎调用。它们由当前用例直接组合，不重新进入 `Processor`，也不各自制造
  一个任务生命周期。
- 澡堂修理、补给等只有在未来被定义为独立插队任务时，才提升为可调度用例并获得
  独立优先级；当前不为其预留通用任务包装。

#### 五、复用策略

- 普通出征、活动出征、演习和战役共享“入口 → 目标/面板 → 编队 → 出征 → 战斗
  → 结果/交接”骨架；模式差异放入 `CombatProfile`/`FleetPolicy`/目标选择策略，
  不复制五套 Runner，也不把差异散落成 `if mode`。
- 决战保留独立阶段状态机，只有在其页面和舰队状态能证明与通用骨架一致后再合并。
- 远征和奖励都采用主页锚点的“检查 → 执行 → 回主页”链路；先复用导航锚点能力，
  不急于制造新的通用物流基类。

#### 六、当前代码的迁移顺序

1. 先让 `BaseExecutor` 只保留执行入口、进度/检查点报告和控制意图读取；移除对
   `dispatch.TaskPaused`、具体页面导航和 `GameContext` 写状态的依赖。
2. 将 `business.system.navigate` 视为临时迁移壳，最终由 infra Navigator 提供；
   新业务代码不再直接导入旧 `autowsgr.ui`/`autowsgr.ops` 页面入口。
3. 演习作为首条垂直切片，接入类型化任务参数、运行时语义能力和 dispatch 状态机；
   用 E2E 验证完整演习、抢占恢复、取消和异常清理。
4. 演习验收后，沿同一骨架迁移普通/活动出征和战役，最后处理决战及剩余后勤用例。
5. 每条链路验收后删除对应旧 Runner/兼容 shim，不保留新旧两条可写执行路径。

### 七、用户确认：业务与导航是两条互补子层

`business` 这一应用层包含两条互补链路，而不是让业务执行器直接操作页面：

```text
业务编排子层  ->  导航编排子层  ->  infra 页面/视觉/设备能力
      \________________业务步骤执行________________/
```

#### 1. 业务编排子层

- 表达要完成的业务目标、步骤、规则、入口锚点和终态锚点。
- 在开始业务动作前请求导航到语义入口；业务未收到入口稳定确认时不得执行后续动作。
- 在步骤边界请求导航到下一个业务所需页面，并报告业务进度、检查点和结果。
- 不负责计算页面路径、识别页面、选择坐标或直接点击页面控件。

#### 2. 导航编排子层

- 持有可追溯的页面/锚点导航图，计算从当前页面到目标入口或安全锚点的路径。
- 执行每一步页面交接并确认目标页面稳定；处理栈漂移、入口页面和最小回退路径。
- 对业务提供语义接口，例如“到达演习面板”“回到主页初始态”“到达战斗准备页”；
  不暴露坐标、模板或 OCR 细节。
- 不决定任务优先级、任务生命周期、业务规则或战斗结果，也不自行创建调度任务。

#### 3. 两条链路的交互

1. `Processor` 选中任务并启动业务执行器。
2. 业务执行器向导航编排请求任务入口；导航到达并确认稳定后返回控制权。
3. 业务执行器执行领域操作；需要页面转换时再次请求语义导航。
4. 收到暂停/取消意图后，业务在最近安全步骤停止并交给导航编排回到安全锚点；
   导航完成确认后，`Processor` 才写入 `paused` 或 `cancelled`。
5. 业务完成后返回结果和下一入口要求；`Processor` 决定下一个任务，导航编排负责
   计算并执行任务之间的最小交接路径。

#### 4. 边界落点

- 导航编排属于 `business` 的互补子层；页面控制器、页面识别、OCR、模板和设备
  操作属于 `infra/base/ui`，二者不能混为一层。
- `business.system.navigate` 可作为迁移期壳保留，但新业务不得继续依赖旧 `ui` 页面
  入口；最终由语义 `Navigator` 统一承接。
- 用户认可当前业务层的反向依赖、旧入口耦合、裸参数和重复状态等问题，具体修正由
  Agent 在后续实现阶段负责；当前先完成层级和交互协议讨论，不立即改生产代码。

## 2026-08-29：前四层架构审查

### 总结

当前 `server -> dispatch -> business/navigation -> infra` 的方向正确，没有需要推倒
重来的层级设计错误；但它仍是概念闭环，尚未形成可执行的唯一控制链。以下问题在第一条
垂直业务切片前必须明确，其他问题可随切片推进。

### 阻塞级问题（先解决）

1. **生产入口仍绕过 dispatch**：HTTP 路由、定时调度器和旧 Runner 仍直接调用
   `ops`/业务函数，Processor 不是实际的唯一任务入口。第一条新业务如果继续这样接入，
   会再次产生两套任务生命周期和两套暂停/取消语义。
2. **业务与导航缺少确认式控制协议**：暂停/取消目前只有信号，没有统一的
   `ControlIntent -> SafeCheckpoint -> NavigationResult -> Processor 状态提交` 事务链。
   必须防止业务尚未停稳时 Processor 提前写 `paused/cancelled`。
3. **导航状态源和路由安全性未收口**：`UIStack.current` 与 `GameContext.current_page`
   仍可能双写；现有 BFS 只按边数找最短路径，未表达原子段、危险边、入口稳定确认和
   临时战斗准备页等安全约束。需要语义锚点、单一页面状态源和带安全条件的路径选择。
4. **业务/战斗代码仍泄漏旧 UI/ops**：`business` 和 `combat` 直接导入旧页面、旧启动
   操作和 `ui.utils`，导航编排与页面实现没有真正隔离；迁移会继续制造循环依赖和无法
   单独验证的执行器。
5. **任务定义到业务输入的边界缺失**：当前链路仍可能把裸 `dict`、HTTP DTO 和 YAML
   路径一路传入执行器。必须在准入阶段完成路径校验、YAML 快照和类型化业务输入，
   执行器不得自行解释外部格式。

### 高优先级问题（随首条切片解决）

1. **运行时和设备 lease 的生命周期需要绑定**：`RuntimeSession`、Processor、旧
   `TaskManager` 与模块级 `GameContext` 的释放/替换时机必须只有一个权威；lease 应
   至少覆盖一次 `ExecutionAttempt`，异常后要先确认设备状态再接收下一个任务。
2. **完成与交接不是一个结果**：业务成功、导航交接成功和任务 `completed` 的先后关系
   必须由一个提交点决定；导航失败要保留业务结果并阻止假成功。
3. **失败后的运行时隔离**：业务异常或清理异常可能留下未知页面/弹窗/战斗状态；下一
   个任务不能只看任务队列为空就继续，必须经过 Runtime/Navigator 的就绪确认。
4. **优先级规则必须只有一个来源**：固定映射、数值方向和严格抢占条件不能同时在
   Processor、Scheduler 和业务执行器中各写一份。

### 可后置但需写明非目标

1. 队列是否跨进程重启持久化；当前可先明确为单进程内存队列。
2. 多账号/多设备并行；当前可先明确一个 RuntimeSession 只服务一个设备。
3. GUI/HTTP 最终 DTO 兼容；继续按约定留到 Kuroko 替换集成阶段。
4. 完整事件回放/断线重放；首批先保证有序事件和可查询的当前任务快照。

### 建议的最小依赖闭环

```text
server / scheduler (只产生 Command)
        -> Processor (唯一任务生命周期写入者)
        -> BusinessExecutor (业务编排)
        -> Navigator (语义导航编排)
        -> infra/base/ui + RuntimeSession (页面、视觉、设备)
        <- BusinessResult / Checkpoint / NavigationResult
```

代码依赖只能向下，运行时结果通过返回值或事件向上回传；不得让 Navigator 反向导入
Business，也不得让 Business 反向导入 Processor 的实现类。共享的任务、锚点和控制数据
放在中立的内部契约模块中，避免用循环导入或通用 EventBus 粘合层级。

## 2026-08-29：宏观架构评判

### 结论

目标架构**总体合理，可以维护，也足够简洁**；不需要增加更多宏观层级。真正的问题是
边界尚未闭合，而不是层数不够。只要把下面的红线收口，这套结构可以作为 Sakuya 的
长期替代架构。

| 维度 | 评判 | 说明 |
|---|---|---|
| 合理性 | 通过 | `server -> dispatch -> business/navigation -> infra` 的控制方向正确；业务编排与语义导航互补，不是重复层。 |
| 可维护性 | 有条件通过 | 单一入口、单一状态所有者和明确的暂停交接协议落地后可维护；保留旧入口和双状态源则不可维护。 |
| 简洁性 | 通过，但需克制 | 四个宏观层级已足够；不要再增加通用 `Manager`、`EventBus`、`WorkflowEngine` 或兼容层。 |
| 清晰性 | 基本通过 | 主链路清楚；`RuntimeSession`/lease、`CombatEngine` 归属和导航子层命名仍需固定。 |

### 绿灯：设计本身没有问题的部分

1. `server` 作为外部适配边界、`dispatch` 作为任务控制中心、`business` 作为业务用例、
   `infra` 作为具体能力实现，分工符合依赖倒置和单向控制流。
2. 业务编排与导航编排放在同一应用层内是合理的：业务需要导航，但导航仍属于业务
   场景语义；页面识别和点击细节下沉到 infra，不需要再造一层“页面业务层”。
3. GUI 契约延后到最终集成不会破坏内部架构，反而避免把旧 DTO 绑定到新实现。
4. 先用 E2E 验证完整业务链、再补最小单测是替代实现分支的合理工程节奏，不是架构缺陷。

### 红线：不收口就会破坏长期可维护性的部分

1. **只能有一个生产入口**：HTTP、定时器、CLI 最终都必须产生同一种内部命令并进入
   `Processor`；任何入口直接调用业务实现都会形成第二套生命周期。
2. **只能有一个任务状态所有者**：`Processor` 写 `TaskInstance` 的生命周期、进度和
   检查点；Business、Navigator、server 只能报告或请求，不能各自维护可写副本。
3. **暂停/取消必须是确认式闭环**：控制意图 → 业务安全点 → 导航安全锚点 → 结果确认
   → Processor 提交状态。仅靠全局事件或异常名称表达暂停不够清晰，也无法证明安全。
4. **运行时资源必须单一归属**：`GameContext`、`RuntimeSession`、设备 lease 和线程
   的创建、替换、释放必须由一个生命周期边界负责；当前“Runtime/Processor 边界”仍
   过于模糊，不能同时存在两个 owner。
5. **新业务不能依赖旧 UI/ops**：否则“业务/导航双子层”只是目录重命名，循环依赖和
   兼容分支会继续增长。

### 黄灯：需要定名和定边界，但不必增加层级

1. **导航命名**：保留 `business` 作为宏观层即可，内部固定为“业务用例编排”和“语义
   导航编排”两个模块；不要把页面导航实现再命名成第三个业务层。
2. **CombatEngine 归属**：它是业务层下面的领域引擎/领域服务，不是 dispatch，也不
   是导航器；它可以有自己的战斗状态机，但不能知道任务抢占或页面路径。
3. **RuntimeSession 归属**：它是运行时基础设施会话，不是任务状态容器；只提供设备、
   OCR、页面能力和资源使用边界，不能与 `GameContext` 并列保存第二份业务状态。
4. **事件数量**：保留一条向上的任务生命周期/业务进度事件流即可；不要为每个子层建立
   独立事件总线。导航结果应作为调用结果或结构化事件返回。
5. **共享契约**：只保留解决真实边界所需的少量值对象（命令、锚点、检查点、结果、
   错误）；不要先把每个步骤都抽象成接口或插件。

### 推荐的稳定宏观图

```text
外部适配：HTTP / Timer / CLI
                │  Command
                ▼
调度控制：Processor ── owns TaskInstance + lifecycle
                │
                ▼
应用业务：Business Use Case
                ├── Semantic Navigator ──> 页面/视觉/设备实现
                └── Combat Domain Engine ─> RuntimeSession
                │
                ▼
运行时能力：RuntimeSession / infra / emulator / vision
```

向下只有命令和语义请求，向上只有结果、检查点和事件；不允许横向互相调用实现细节。
这个图已经足够表达系统，不建议再引入新的宏观层级。

## 2026-08-29：共享导航器归属与调用关系（提案）

### 结论

导航器应当**独立职责、单一实例、并排复用**，而不是分别创建“调度导航器”和“业务
导航器”。它仍属于业务应用层内部的导航编排子层，不升格为新的顶层架构层。

```text
外部适配 -> Processor
                ├─ 选择任务 / 决定何时交接
                ├─ 调用共享 Navigator 完成任务入口或任务间交接
                └─ 调用 BusinessExecutor
                                └─ 调用同一个 Navigator 完成业务步骤导航

共享 Navigator -> RuntimeSession -> infra/base/ui / vision / emulator
```

### 三个“决定”必须分开

| 问题 | 所有者 |
|---|---|
| **何时导航、为什么导航**（启动、暂停、取消、任务交接） | `Processor` |
| **业务需要哪个语义锚点**（演习面板、战斗准备、下一轮入口） | Business 用例 |
| **如何从当前位置到达锚点**（路径、边安全性、页面确认） | `Navigator` |

因此，调度层可以判断“下一任务需要进入哪个入口”，但不能自己计算页面路径；业务层
可以请求“到达哪个业务步骤”，但不能自己点击页面；两者都调用同一个导航器实例。

### 调度与业务的调用边界

1. 每类任务在类型化任务元数据中声明入口锚点、恢复锚点、取消/终态锚点和上下文复用
   约束；`Processor` 只读取这些声明，不导入业务执行器内部实现。
2. `Processor` 选中任务后，调用 `Navigator` 到达任务入口；到达且稳定确认后才启动
   Business 用例。
3. Business 在执行过程中调用同一个 `Navigator` 到达内部步骤锚点；导航结果作为
   调用结果返回，不改变任务生命周期。
4. 任务暂停、取消或完成时，`Processor` 决定交接目标；`Navigator` 执行从当前真实
   锚点到目标锚点的最短安全路径。
5. `Navigator` 不知道任务类型、优先级和下一个任务，也不创建任务；Business 不决定
   下一个任务；`Processor` 不知道坐标、模板和页面点击细节。

### 为什么不采用两套导航器

- 两套导航图会产生不同的最短路径和安全规则。
- 两套“当前页面”状态会再次制造状态竞争和栈漂移。
- 暂停/恢复时无法证明调度器看到的页面与业务看到的是同一个页面。
- 任何导航 bug 都需要在两处修复，违背简洁和单一事实来源。

### 共享导航器的边界约束

- 一个 `RuntimeSession` 对应一个 `Navigator`；不使用全局导航器，也不为调度和业务各
  建一个实例。
- `Processor` 串行化导航调用；`Navigator` 不自带任务队列、线程或事件总线。
- Navigator 对外只暴露语义锚点和结构化到达结果（到达锚点、是否稳定、错误）；页面
  控制器、OCR、坐标和设备操作留在 infra。
- 业务的入口/安全点声明是数据契约，不在 `Processor` 和 Business 中各写一份路径
  规则；路径规则只在 Navigator 中维护。

### 宏观判断

“导航器和业务独立，并排成同一应用层”是更好的方案；“调度器拥有一套导航器、业务
再拥有一套导航器”是不合理的方案。前者既满足调度层任务交接需求，又保留业务层对
导航的依赖，同时没有增加新的宏观层级或重复状态源。

### 任务之间衔接能力的归属澄清

这里要把“任务衔接决策”和“页面导航执行”拆开：

- **任务衔接能力的业务责任归 `dispatch/Processor`**：它负责在任务 A 结束、暂停、
  取消或失败后，结合任务 B 的入口声明、A 的实际终态、上下文复用条件和恢复策略，
  决定是否需要衔接、衔接到哪个语义锚点，以及何时允许启动 B。
- **衔接路径的执行责任归共享 `Navigator`**：它接收起点锚点、目标锚点和安全约束，
  计算并执行最短安全路径，确认页面稳定并返回结果。
- **任务自身只声明边界，不决定其他任务**：Business 用例声明自己的入口、暂停/取消
  安全点和终态锚点；不负责选择下一个任务，也不负责决定任务 A 到任务 B 的交接策略。

因此，任务间衔接不是 Business 的职责，也不是 Navigator 的完整职责，而是：

```text
Processor：决定 A → B 是否衔接、目标是什么、何时提交状态
Navigator：执行从当前锚点到目标锚点的安全路径
Business：声明自身边界并报告实际终态
```

`Processor` 可以持有一个轻量的“衔接策略”概念，但不应再创建一个独立的调度导航器。
若衔接规则将来明显膨胀，可在 `dispatch` 内提取 `HandoffPolicy/Coordinator`；它仍
属于调度职责，且必须调用同一个 Navigator。

## 2026-08-29：业务域细分与 Runner 边界（提案）

### 一、导航职责的精确定义

`Business` 不再负责任务之间的导航，也不拥有导航图、路径计算、页面识别、OCR 或点击。
它仅声明某个业务步骤开始前必须满足的语义锚点，例如“演习面板已稳定”或“战斗准备页已稳定”。
共享 `Navigator` 负责到达和确认该锚点；`Processor` 负责任务 A 到任务 B 的衔接决策。

因此，业务用例可以提出“我需要哪个锚点”的前置条件，但不能自行决定“从哪里怎么走”。这不
是让 Business 再次承担导航，而是保持业务步骤的可读前置条件。

### 二、业务域只分为战斗和港区两类

建议保留两个一级业务域，不再增加第三个宏观业务层：

```text
business/
  combat/                 普通出征、活动出征、演习、战役、决战
  homeport/               拆解、改装、建造、澡堂维修、远征、任务、后院具体功能
  fleet_policy.py         已被真实场景复用的编队规则数据
```

代码目录使用 `homeport`，文档中继续称为“港区域”。`logistics` 不能准确表达拆解、
改装、建造、任务和后院；`homeport` 明确表达这些发生在游戏内港区，且不会与技术端口混淆。这里不是再造一个
“共享业务层”：`fleet_policy.py` 仅保留已有的、跨战斗与远征确实共用的规则。

### 三、战斗域的最小切分

| 用例 | Runner/Executor | 原因 |
|---|---|---|
| 普通出征、活动出征 | 一个 `SortieExecutor` | 当前两者主流程相同，差异是入口和计划数据；不得保留第二个活动 Runner。 |
| 演习 | 一个独立 Executor | 对手选择、次数语义和结束条件不同。 |
| 战役 | 一个独立 Executor | 入口、编队方式和流程不同。 |
| 决战 | 一个独立 Executor | 自有章节状态、编队和多阶段流程，不应塞进通用出征分支。 |

普通/活动出征的差异放入类型化的出征规格，例如入口、地图、难度和计划；不能在同一个
Runner 中逐渐堆积无法审计的 `if event` 分支。当前 `EventFightRunner` 已经只是
`NormalFightRunner` 的薄包装，这证明合并方向正确。

### 四、编队、OCR 和快速维修

1. 编队的页面识别、OCR、点击、换队操作属于 `infra`，只提供“读取当前编队”和“执行选择”
   能力；不包含模式业务规则。
2. `fleet_policy.py` 只描述不同用例的规则，例如可选舰队、是否逐格填船、首位是否必填、
   换队限制。普通出征、演习、战役、决战和远征按实际需要传入各自规则。
3. 不建立抽象基类、工厂或“FleetRunner”。现有 `FleetPolicy` 这种小型不可变规则数据已经
   足够；规则确实不同才增加字段或明确分支。
4. 快速维修发生在战斗准备页，是当前战斗任务为继续出征而执行的原子步骤：不进入队列、
   不拥有独立 `TaskInstance`、不单独接受取消或优先级。它应归 `combat` 的准备阶段，而不
   是港区维修 Runner。
5. 澡堂维修是独立港区任务，可以由用户或定时器提交，拥有自己的结果和调度优先级。两者可
   共用低层页面/视觉能力，但不能强行共用业务策略或生命周期。

### 五、港区 Runner 的判定标准

拆解、改装、建造、澡堂维修、远征、任务领取，以及后院中每个有独立业务结果的动作，都可
拥有各自的 Executor。判断标准不是“它在一个页面上”，而是它是否可以被用户或定时器独立
提交、取消、展示状态并返回结果。

因此不创建笼统的 `BackyardRunner`：后院是页面区域，不是单一业务目标。后院中的实际动作
（例如食堂收取、烹饪或其他已确认功能）在功能迁移时按独立结果拆分。建造也在真正开始迁移
时再依据“开始建造”和“收取完成品”是否需要独立生命周期决定 Runner 粒度，当前不预造空壳。

同一动作如果既能独立提交、又可能是另一任务的必要原子步骤，应复用低层能力而非互相调用
Runner。快速维修是已经确认的例子；战斗因船坞满而触发的自动拆解也应在迁移时按同一规则
审查。

### 六、业务包组织方式（用户确认）

每个可被 `Processor` 独立调度的业务用例使用一个目录包，包内只有一个统一业务入口：
`executor.py` 中的 `XxxExecutor`。这不是要求每个按钮或辅助函数都建包，而是让每个可独立
提交、暂停、取消、展示状态并返回结果的业务模块拥有清晰的责任边界。

```text
business/
  combat/
    sortie/                 # SortieExecutor：普通/活动出征
      __init__.py           # 仅导出 SortieExecutor
      executor.py           # 业务流程和检查点
      spec.py               # 入口、地图、难度、计划数据
    exercise/               # ExerciseExecutor
      __init__.py
      executor.py
      rivals.py             # 对手选择确有独立规则时保留
    campaign/               # CampaignExecutor
      __init__.py
      executor.py
    decisive/               # DecisiveExecutor
      __init__.py
      executor.py
      chapter.py            # 决战独有章节流程
      state.py              # 决战独有状态

  homeport/
    destroy/                # DestroyExecutor
    retrofit/               # RetrofitExecutor，迁移时再创建
    build/                  # BuildExecutor，迁移时再创建
    bath_repair/            # BathRepairExecutor
    expedition/             # ExpeditionExecutor
    mission/                # MissionExecutor
    backyard/               # 仅按已确认的实际动作继续细分
```

一个包初始可以只有 `__init__.py` 和 `executor.py`；当且仅当出现独立的职责时，再加入
`spec.py`、`rules.py`、`state.py`、`checkpoints.py` 或具体子流程文件。不得为了整齐预建空
文件，也不得把无关逻辑塞进 `utils.py`。`executor.py` 只编排步骤、处理检查点并返回业务
结果，不放 OCR、坐标、页面点击、导航路径或通用规则。

以下模块不是可调度任务，因此不设 `XxxExecutor`：

- `navigation/`：`Navigator`、锚点、图和到达结果；
- `business/combat/engine/`：战斗状态机和战斗领域规则；
- `business/fleet.py`：小型、纯粹的编队规则数据；
- `infra/` 下的页面、OCR、模板和设备能力。

`__init__.py` 只导出明确的公开对象，不能执行注册、副作用、兼容路由或维护状态。调度器仍
通过自身的显式任务注册表找到 `XxxExecutor`，不让业务包 import 时隐式改变系统状态。

### 七、港区域命名修订（已确认）

此前使用的 `port` 不再作为推荐代码目录名。它在后端代码中容易被理解成网络端口、适配器
端口或接口边界，不能稳定表达游戏内的“港区”业务域。

最终使用 `homeport`：它明确表示游戏内港区，且能覆盖拆解、改装、建造、澡堂维修、远征、
任务与后院功能；中文架构概念仍称“港区域”。在实际迁移该业务时再创建或重命名生产目录。

### 八、现有基建层盘点（事实，不是迁移方案）

当前 `infra` 是迁移中的目录，不是已经完成的最终基建层：

```text
autowsgr/
  infra/                    # 配置、日志、异常、文件工具、常量、部分物理 UI
  emulator/                 # 设备连接、截图、触控、模拟器控制
  vision/                   # OCR、模板匹配、像素/ROI 识别
  ui/                       # 大部分旧页面控制器与页面工具
  data/                     # 图片、OCR 模型、地图与计划等包资源
  context/GameContext       # 当前混合的运行时、游戏状态、导航和停止状态容器
```

已经有价值、应当保留并逐步收口的基础能力包括：配置、日志、异常、受控文件操作、设备控制、
截图、视觉识别、页面识别、物理页面动作、包资源读取和页面导航图。

当前不能直接作为最终边界的部分包括：

1. `infra/base/ui/navigation.py` 有物理页面图和 BFS，但导航边仍直接导入旧 `ui` 页面实现；
   它只能作为过渡资产，不能让新业务依赖旧 UI。
2. `business/system/navigate.py` 同时做页面识别、重试、栈同步和 `current_page` 写入，和下层
   导航图形成双重导航所有权。
3. `GameContext` 同时持有控制器、OCR、配置、游戏快照、导航栈、计数器和停止事件；
   `server.TaskManager` 又持有一份停止事件，违反单一状态所有者。
4. `infra/base/data`、`matcher`、`ocr` 目前只是空壳，不能先按名称继续堆模块。

下一步讨论的不是立刻移动文件，而是给这些能力定出唯一的长期所有者：运行时会话、基础设施、
物理 UI、语义导航器和任务/游戏状态各自负责什么。这样首个演习垂直切片才不会再次依赖新旧两套
实现。

### 九、基建能力的初步分类（待讨论，不是代码迁移清单）

| 类别 | 现有来源 | 初步判断 |
|---|---|---|
| 设备控制 | `emulator/controller/AndroidController`、Scrcpy、设备探测 | 已有清晰的低层能力；保持“截图、触控、应用、连接”边界，不进入业务规则。 |
| 视觉感知 | `vision/` | 已有像素、模板、OCR、ROI 等能力；保持无业务含义的识别结果，不在此处加入任务/页面流程。 |
| 物理 UI | `ui/` 与部分 `infra/base/ui/pages/` | 应包含页面识别、页面原子动作和浮层处理；当前新旧实现混用，是主要迁移对象。 |
| 页面目录/导航图 | `ui.page`、`UIStack`、`infra/base/ui/navigation.py` | 目录目前是 import 副作用的全局可写注册表，栈又被塞进 `GameContext`；最终需要由共享 Navigator 明确持有自己的导航会话状态，并使用一个清晰作用域的页面目录。 |
| 设备互斥 | `server/device_lease.py` | 保护的是物理设备而非 HTTP；长期应随 `RuntimeSession` 的设备资源存在，Processor 使用 lease 执行任务但不把它变成第二个任务状态机。 |
| 静态资源 | `data/`、`image_resources/` | 图片、OCR 模型、地图、计划和模板查找属于只读包资源；不属于业务域，也不应为了目录整齐而全量搬迁。 |
| 横切基础能力 | `infra/config.py`、`logger.py`、`exceptions.py`、`file_utils.py` | 配置、日志、错误和受控文件操作属于真正基础能力；其中运行期全局延迟参数以后需纳入会话配置边界，不能继续成为隐式跨会话状态。 |

这里的关键不是把所有东西塞进一个更大的 `infra/` 目录，而是禁止它们继续通过 `GameContext`、
全局变量或 import 副作用互相取得可写状态。已有清晰底层实现就保留；只把所有权不清、方向倒置或
新旧混用的部分纳入迁移。

### 十、视觉、静态资源与运行时状态的边界（提案）

#### 1. 基础方法与基础常量分开，但“坐标”不是代码常量

这个方向正确。代码常量只保留真正不会随页面校准、分辨率或活动变化的程序语义，例如枚举、
优先级范围和页面键。坐标、OCR 区域、色彩签名、模板元数据属于 **UI 校准资源**，应以只读
数据文件维护，按页面/界面版本组织；设备操作继续使用现有的相对坐标约定。它们不能散落在业务
代码、页面方法和 Python 常量中。

#### 2. CV2、FastOCR 与 YOLO 的职责

CV2 不能通用替代 OCR：它擅长定位、裁剪、颜色/模板/几何判断和 OCR 前处理，但不能可靠读出
任意舰名、数值或动态文本。有限且样式固定的目标（图标、选中状态、按钮、固定枚举）优先用
CV2/模板匹配；只有需要读文字或数字时才在已定位的 ROI 上调用 OCR。这样 CPU 默认运行时既
减少 OCR 次数，也保留语义识别能力。

FastOCR 是唯一的目标 OCR 技术栈；EasyOCR 不应长期作为并行能力或静默 fallback。删除 EasyOCR
依赖必须等所有现有文字识别路径完成 FastOCR 覆盖盘点并在实际切片中验证之后，不能先删再补。

当前不引入 YOLO，也不启动模型训练。游戏 UI 的元素位置、颜色和结构相对稳定，现有 CV2 +
校准资源足够；YOLO 会引入标注集、模型版本、CPU 推理开销和模型发布生命周期。只有在真实多
分辨率/活动界面下，CV2 规则已经有可复现的定位失败且继续增加模板/规则明显不可维护时，才把
YOLO 作为有证据的升级项重新评估。

#### 3. `data` 是只读包资源，不是所有数据的归宿

现有 `data/` 可以继续承载图片、OCR 模型、地图、内置 YAML 模板和参考资料；语义上称为“包资源”。
用户通过 GUI 编辑的 YAML、运行日志、任务进度和游戏快照不属于它，必须位于受控的用户数据目录。
后端接到 YAML 路径后应校验允许目录，并生成不可变 `TaskDefinition` 快照，而不是把可变文件句柄
挂入长期上下文。

`image_resources` 是对包资源的模板索引，可以保留；没有必要为了目录整齐全量搬迁或新增一层资源
抽象。开发/诊断脚本可以放入顶层 `tools/`，但 `tools/` 不能被运行时业务导入，也不能成为新的
通用工具垃圾桶。

#### 4. UI 只提供物理能力；语义导航不放在 UI

UI 负责页面识别、页面原子动作、弹窗和等待确认，作为 Navigator 的下层能力。Navigator 负责
语义锚点、路径选择、到达验证及其私有导航状态；它不是 UI 包内的另一个页面工具。UI 不拥有任务
优先级、任务衔接或业务规则。

#### 5. 不保留一个新的万能 `context`

Processor 只拥有 `TaskDefinition`、`TaskInstance`、`ExecutionAttempt` 的任务生命周期、优先级、
暂停/取消意图和终态提交。它可以在每次执行时显式传入所需依赖，但不能把设备、OCR、页面栈、
游戏快照和业务局部状态塞进自己持有的可写 Context。

长期所有权应保持分开：RuntimeSession 管理设备、OCR、配置、包资源访问和设备 lease 的创建/释放；
Navigator 管理导航会话状态；游戏快照由独立游戏状态所有者管理；Executor 只保留一次执行尝试的
局部状态。这样 YAML 定义、任务生命周期、运行时资源和游戏事实不会因暂停/恢复被错误地一起复制、
重置或持久化。

### 十一、坐标集中引用与上下文生命周期（提案）

#### 1. 坐标可以集中管理，但业务不应直接依赖坐标

用户希望通过 `XXX.XXX.XX` 统一引用坐标和常量，这个维护目标正确；但最终不应让业务代码变成
`Constants.BATTLE.PREP.START_BUTTON` 的调用者。否则坐标虽然集中，业务仍然知道了页面几何，
以后页面改版仍要修改业务。

建议保留两层接口：

```text
基础设施/诊断代码：session.ui_profile.coordinates.battle_prep.start_battle
业务代码：         session.ui.battle_preparation.start()
```

前者是集中校准数据的类型化点号访问，后者是业务可用的语义能力。页面能力内部读取 `UIProfile`，
业务只表达“开始出征”“选择舰队”“读取当前编队”等语义动作。

#### 2. 不建立一个巨型 `Constants`

需要分成四类：

| 类别 | 内容 | 归属 |
|---|---|---|
| 程序常量 | 枚举、页面键、Android 键值、优先级上下限 | `infra`/代码常量，类型化且不可变 |
| UI 校准数据 | 点击坐标、探测点、OCR ROI、颜色、像素签名、模板元数据 | `UIProfile` 加载的只读 `data` 资源 |
| 包资源 | FastOCR 模型、图片、地图、内置 YAML 模板 | `data`/`image_resources`，只读 |
| 业务策略 | 编队规则、停止条件、任务优先级语义 | `business` 用例或领域规则 |

当前 `infra/base/constants/coordinates`、`colors`、`ocr`、`signatures` 已经是这条路的部分实现，
应复用其 YAML 加载和点号路径能力，后续再加类型化命名空间、范围校验和按设备分辨率选择。不能
通过新增一个平铺的大文件解决问题。

这里的“类型化命名空间”是明确字段的普通数据对象，不是用 `__getattr__` 允许任意路径的动态魔法；
未知坐标键应在加载或构造时失败，避免把拼写错误拖到实机点击阶段。

#### 3. 上下文按作用域拆分，而不是按“有没有任务”二分

“任务未结束就不能清空”需要保留，但保留的是可恢复的语义状态，不是所有运行时对象：

```text
Processor
  └─ TaskInstance             任务生命周期、定义快照、优先级、终态、检查点
       └─ ExecutionAttempt     一次运行的局部步骤、临时识别结果、尝试结果

RuntimeSession                设备、FastOCR/CV2、UIProfile、Navigator、设备 lease
  └─ GameStateStore            跨任务游戏观测：舰船、资源、远征、当前可用事实
```

四者的生命周期不同：

| 对象 | 创建/销毁 | 应保存什么 |
|---|---|---|
| `TaskInstance` | 接受任务 → 终态 | YAML 不可变快照、状态、进度、检查点、结果摘要 |
| `ExecutionAttempt` | 开始一次执行 → 完成/暂停/失败 | 当前步骤和临时变量；暂停后可销毁，不能作为恢复依据 |
| `RuntimeSession` | 设备会话建立 → 进程/设备会话结束 | 设备与视觉资源、校准 profile、导航器和 lease |
| `GameStateStore` | 会话建立 → 会话结束（必要事实可持久化） | 带时间戳/来源/置信度的语义观测，不保存原始 CV2 中间产物 |

因此，暂停时任务对象不会清空，但执行器可以退出；Processor 保存 checkpoint，恢复时重新创建
`ExecutionAttempt`，由 Navigator 回到安全锚点。完成或取消后释放尝试级状态，但保留最终结果和
审计所需的任务记录；RuntimeSession 是否继续存在取决于是否还有后续任务。

#### 4. 业务产出的分发路径必须只有两条

```text
CV2/FastOCR → UI 页面能力 → 语义观测
                              ├─ 仅当前步骤使用：留在 Executor 局部变量
                              └─ 跨任务仍有意义：GameStateStore.apply(observation)

Executor → Progress / Checkpoint / Result → Processor
                                              └─ 状态提交、持久化、GUI/WS 通知、调度决策
```

Processor 是任务事件的唯一分发者；`GameStateStore` 是游戏事实的唯一写入者。Executor 不直接
写 `TaskInfo`、不直接广播 GUI，也不把每次 OCR 结果塞进共享上下文。当前步骤需要的结果直接返回
给当前调用者；只有进度、检查点、终态结果和明确的跨任务观测才向上分发。

`GameStateStore` 是所有权和接口边界的名称，不是现在就要搭建的通用状态框架。首个演习切片只
实现它实际需要的最小类型聚合和更新入口；没有第二个真实消费者前，不创建通用 reducer、仓储层
或 EventBus。

#### 5. 对当前 `GameContext` 的迁移映射

`ctrl`、`ocr`、`ship_ocr`、配置 → `RuntimeSession`；`ui_stack`、`current_page` → `Navigator`；
资源、舰队、远征、建造、澡堂和舰船注册表 → `GameStateStore` 的语义状态；每日掉落计数按其
是否跨任务保留归入游戏状态；`active_fight_tasks`、`stop_event` → Processor 的任务状态；
`sync_before_combat` / `sync_after_combat` → 业务结果到 `GameStateStore` 的显式 reducer/更新入口。

这让“上下文伴随任务”保留下来，但不再让一个对象同时拥有设备、导航、任务和游戏事实。

## 2026-08-30：入口与 Processor 的顶层链路（待确认）

### 一、统一入口模型

所有会改变游戏设备状态的外部入口都只做适配，不执行游戏逻辑：

```text
GUI HTTP / Timer / CLI
        ↓
入口适配器：传输校验、来源标记、DTO → Command
        ↓
Processor：语义校验、YAML 快照、任务实例、队列与生命周期
        ↓
Executor：业务步骤
        ↓
RuntimeSession + Navigator + emulator/vision/UI
        ↓
TaskEvent / TaskResult → HTTP 状态查询与 WebSocket 投影
```

入口适配器不得创建执行器、读取业务 YAML、直接点击设备、维护任务状态，
也不得为了绕过队列而调用旧 `TaskManager` 或 `TaskScheduler`。

### 二、Command 与任务的区别

- `Command` 是一次短暂的外部意图，例如“提交这个 YAML”“取消 task-123”；
  建议使用不可变数据对象，不把 FastAPI DTO 或可变 `dict` 直接传入业务。
- `TaskDefinition` 是 Processor 在准入时从允许目录读取并冻结的 YAML 快照。
- `TaskInstance` 是 GUI 看到的逻辑任务，拥有唯一 `task_id`、优先级、状态、
  进度、检查点、结果和错误；暂停/恢复不创建新的实例。
- `ExecutionAttempt` 是一次实际执行尝试，暂停后可以销毁并重建。

第一阶段只需要 `SubmitTaskCommand` 和 `CancelTaskCommand` 两个真实命令；
没有多个实现前，不建立 CommandBus、Factory 或 EventBus。

### 三、各入口的行为

1. **HTTP**：Pydantic 只验证 JSON 形状和基本范围；路由转换为命令后调用
   同一个 Processor。提交接口返回 `task_id + accepted/queued/running`，
   完成结果通过状态查询或 WebSocket 获取。`/api/ops/*` 的设备写操作也必须
   走此路径；只读查询可以直接读取 Processor/GameStateStore 的投影。
2. **Timer**：定时器只判断“是否到时间”并产生同样的提交命令，不再维护第二个
   执行队列、任务状态或 Runner 循环。现有 `TaskScheduler` 只能暂时保留为
   触发源兼容层，最终不能与 Processor 并列拥有任务队列。
3. **CLI**：参数解析后直接调用 Processor，不通过 HTTP 回环；需要同步体验时
   只等待同一个任务实例的终态。

### 四、Processor 的准入与调度顺序

```text
Command
  → 运行时是否 READY
  → YAML 路径/任务类型/参数是否有效
  → 由任务类型画像确定 0..10 优先级
  → 创建 TaskInstance 并入队
  → 当前无任务则运行；有任务则按暂停能力决定抢占或等待
```

路径安全、YAML 结构、注册表存在性和业务参数属于 Processor 的语义校验；
HTTP 只负责传输层校验。GUI 不能任意覆盖业务优先级，最多提交明确约定的
业务选项。Processor 是唯一修改任务生命周期和发送任务事件的对象。

### 五、系统生命周期不等于任务生命周期

`system_start/stop` 由应用组合根（暂名 `RuntimeHost`）管理，不作为普通游戏任务
塞进 Processor：

- `start` 创建 `RuntimeSession`（设备、视觉、UIProfile、Navigator、lease），
  再创建并启动该会话唯一的 Processor。
- `stop` 先让 Processor 停止接收新任务并协调当前任务取消/回主页，确认执行线程
  退出后，再关闭 RuntimeSession；超时则保留会话，不得提前释放设备或上下文。
- 任务提交发生在 RuntimeSession 未 READY 时应被拒绝，并返回明确的“系统未启动”
  状态，而不是在路由中临时创建上下文。

### 六、三个业务场景

**GUI 启动演习**：HTTP 校验 `{task_type, yaml_path, overrides}` → 构造
`SubmitTaskCommand` → Processor 读取并冻结 YAML、分配演习优先级、创建 task →
立即返回 task_id → Processor 在自己的 worker 中构造 `ExerciseExecutor`；进度和
终态由 Processor 发布。

**演习中定时远征**：Timer 产生 `SubmitTaskCommand(expedition_check)` → Processor
发现远征优先级更高，向演习实例发出暂停意图 → Executor 在安全断点回主页并上报
checkpoint → Processor 运行远征 → 通过同一个 Navigator 完成任务交接 → 恢复原
演习实例。Timer 不直接调用远征 Runner。

**用户取消**：HTTP 产生 `CancelTaskCommand(task_id)` → Processor 设置取消意图；
Executor 在最近安全点停止并回主页 → Processor 保存清理结果并将任务标记为
`cancelled`。路由不直接操作 `stop_event` 或 worker thread。

### 七、迁移时的唯一收口点

现有 `TaskManager` 的任务状态、停止信号、worker 和通知职责逐步并入 Processor；
现有 `TaskScheduler` 的执行队列逐步删除，只保留定时触发适配。迁移期间可以保留
兼容 facade，但 facade 只能转发到 Processor，不能再保存第二份可写状态。

以下四条作为入口层定稿候选，待用户确认：

1. 所有设备写操作（战斗、远征、奖励、维修、建造等）统一提交 Processor。
2. `system_start/stop` 属于 RuntimeHost，不属于普通任务队列；`system_stop` 必须
   先协调 Processor 再释放 RuntimeSession。
3. HTTP/Timer/CLI 共用同一 Processor 实例和同一任务状态源，HTTP 返回受理结果，
   终态通过状态查询/WS 获取。
4. 优先级由 Processor 按任务类型画像统一计算，内部范围固定为 `0..10`。

## 2026-08-30：入口至 Processor 的完整控制面（待逐项定义）

用户确认公开入口只保留两类：后端 CLI 和 GUI HTTP；两者先经过指令识别/转换，
再进入 Processor。这个方向成立，但需要先区分“外部入口”与“运行时控制”：

```text
旧 CLI 脚本 / 新 CLI                 GUI HTTP
          │                              │
          └────── 输入适配与兼容转换 ─────┘
                         │
              ┌──────────┴──────────┐
              │                     │
        RuntimeControl          TaskCommand
              │                     │
        RuntimeHost          Processor
        (启动/停止)      (接受/排队/执行/取消)
```

`RuntimeHost` 不是第三种入口，而是系统启动/关闭的内部宿主；Processor 无法在自身尚未
存在时负责创建设备会话。Timer 也不是第三个公开入口：它可以由 GUI、后端或兼容脚本持有，
到时间时只产生与 CLI/HTTP 完全相同的 `TaskCommand` 后提交 Processor，不能直接调用业务
执行器。GUI 关闭后是否仍需后端继续定时，是产品层面的选择，不改变这条任务契约。

### 一、兼容转换的真实边界

`python` 和 `uv` 是 shell/解释器启动方式，不是后端可以安全解析的业务指令。
`uv run python old.py ...` 启动后，进程通常只得到 `old.py` 的 argv。因此不实现
“接收任意 shell 字符串并执行”的转换器，也不引入 `shell=True`。

兼容方案必须是显式的：每个被承诺兼容的旧脚本或旧公开函数，在它已经取得结构化参数后，
调用一个小型适配函数，把旧参数转换为新 `TaskCommand`；不支持的旧调用给出明确迁移错误。
需要建立兼容矩阵，区分：

1. 用户启动任务的旧脚本/API：迁移为 facade；
2. `auto_daily` 这类“启动运行时 + 安装定时策略”的旧入口：拆为 RuntimeControl 和
   内部定时命令生产者，不能伪装成一个普通战斗任务；
3. E2E、调试、迁移和维护工具：仍是工具，不自动纳入生产任务契约。

### 二、最小命令词汇

先不要创建通用 CommandBus。第一阶段只需明确以下意图：

| 分类 | 命令 | 去向 | 说明 |
|---|---|---|---|
| 运行时 | `StartRuntime` / `StopRuntime` | RuntimeHost | 配置、设备会话的建立与释放。 |
| 任务 | `SubmitPlan` | Processor | 提交一个 YAML 定义的任务。 |
| 任务 | `CancelTask` | Processor | 取消运行中或排队任务。 |
| 查询 | `GetRuntime` / `GetTask` / `ListQueue` | 只读投影 | 不是命令，不改变状态。 |

是否还需要 `SubmitAction`（没有 YAML 的一次性动作，如立即收奖励、收建造、澡堂维修）
必须由业务定义决定。架构建议是不强迫没有持久配置的一键动作制造 YAML；它们可以使用
同一个 Processor 的类型化任务命令。若产品坚持“所有 GUI 写操作只给 YAML 路径”，则必须
为这类动作定义内置任务 YAML 或 GUI 生成的任务文件，代价是更多文件和间接层。

用户手动暂停、手动恢复、重试不是默认命令；只有 GUI 确有该业务能力时才加入。

### 三、YAML 契约必须分为四部分

1. **路径契约**：GUI 传任务 YAML 的位置；后端规范化并要求它位于配置的允许任务根目录，
   拒绝不存在文件、目录、非 YAML、越界软链接和任意磁盘读取。第一阶段可以采用“绝对路径 +
   单一允许根目录”，不先引入多 root ID 体系。
2. **文档契约**：新 YAML 从第一天起必须含 `schema_version` 与稳定的任务种类；
   任务种类、显示名和业务配置分层。YAML 不保存运行进度、优先级、设备状态、坐标或 Python
   可执行表达式。
3. **覆盖契约**：GUI/CLI 的额外字段只能是任务类型明确声明的类型化 launch options；
   禁止把任意嵌套 `dict` 深合并到 YAML。最终生效定义和覆盖来源必须进入任务快照。
4. **快照契约**：Processor 读取一次、解析、校验、冻结并记录源路径/版本/内容指纹；
   GUI 后续修改同一文件不影响已接受任务。

当前包内旧战斗计划 YAML 没有 `task_type`，而现有 `Request.from_yaml()` 却假定它存在，
二者不能直接作为最终契约。迁移期间由兼容转换器根据旧命令或旧计划目录补出任务种类，再
产生统一的不可变 `TaskDefinition`；业务 Executor 不应同时承担新旧 YAML 解析分支。

### 四、Processor 必须具备的控制能力

- 运行时 READY 校验和单设备单活跃任务保证；
- 命令去重：GUI/CLI 提供 `client_request_id` 或幂等键，网络重试不得创建两份任务；
- 接受结果：`accepted`、`queued`、`deduplicated`、`rejected`，与最终执行结果分开；
- 任务状态机：至少 `queued → running → paused/resumed → completed/failed/cancelled`；
- 同优先级 FIFO、高优先级安全抢占、不可打断原子段延后，以及定时任务重复触发的合并规则；
- 取消排队任务与取消运行任务的不同处理；
- 一个 Processor 自己拥有的串行 worker，不让 HTTP route、Timer 或旧 TaskManager 各自创建
  独立执行线程；
- 任务快照、进度、checkpoint、根因、清理结果和事件序号的唯一写入与通知；
- 进程重启时的策略：首阶段可明确标记未完成任务为 `interrupted`，是否持久化/自动恢复由
  后续业务要求决定，不能隐式假装恢复成功。

### 五、GUI/CLI 对外契约需要提前保留的字段

提交至少需要来源、计划引用、额外启动选项和幂等键；Processor 返回服务器生成的 `task_id`。
状态与 WebSocket 事件必须带 `task_id`、状态、进度、事件序号/版本和时间，GUI 断线后可用
查询接口重新拉取权威快照。错误应分为输入/转换/准入/执行四类并给出稳定错误码，不能把 Python
异常文本当作 GUI 契约。

### 六、需要用户逐项定义的业务决策

1. 所有可调度业务是否都必须由 YAML 定义，还是保留 `SubmitAction` 给无配置的一键港区操作；
2. 新 YAML 的任务种类命名和每个种类的业务字段；
3. GUI 传绝对 YAML 路径的允许根目录，以及 GUI 保存完成与后端读取之间的约定；
4. GUI 允许哪些临时覆盖字段，覆盖与 YAML 冲突时谁优先；
5. 哪些旧脚本、旧 Python API、旧日常挂机入口属于必须兼容的公开入口；
6. GUI 的“执行队列”是多个独立 TaskInstance，还是需要一个可取消/可排序的父级任务组；
7. Timer 的触发来源、相同任务重复触发时是合并、忽略还是再排队；
8. 用户是否需要手动暂停/恢复/重试，还是仅支持取消；
9. 后端重启后未完成任务的产品语义；
10. Sakuya 第一阶段是否明确只支持一个本地 RuntimeSession/模拟器。

## 2026-08-30：入口控制面的业务化解释与最小默认规则

用户进一步明确：GUI 以 YAML 驱动任务；后端执行的最小边界是“一次任务”；需要重复执行
时由定时/空闲触发器再次提交任务。因此入口和 Processor 的设计先按业务行为定义，内部
术语不应反过来成为新的架构层。

### 一、把术语还原成业务对象

- **系统开关**：负责连接模拟器、准备游戏和关闭设备会话。它只回答“系统能不能接任务”，
  不执行某个战斗或港区任务。此前图中的 `RuntimeHost` 只是这个系统开关的内部持有者。
- **任务单**：入口把 CLI 或 HTTP 请求翻译成一张统一的任务单，再交给 Processor。此前图中
  的 `TaskCommand` 只是任务单的内部数据，不需要先搭建 CommandBus 或其他消息基础设施。
- **任务处理器**：像调度台，负责检查任务单、排队、执行、暂停、恢复、取消、记录状态并
  通知 GUI。任务单进入这里以后，就已经是 AutoWSGR 的内部业务请求。

因此公开入口仍然只有两层：

```text
CLI / GUI HTTP
      ↓
识别旧写法并转换成统一任务单
      ↓
Processor
```

系统开关是启动/停止的宿主，不是每张任务单都要经过的额外业务层。

### 二、一次任务的业务边界

1. 一份 YAML 描述一次可执行的业务任务；任务被接受后生成一个唯一 `task_id`。
2. 任务完成、失败或取消后即结束，不在 Processor 内隐式循环。
3. 定时执行、空闲执行和挂机不是一个无限任务，而是一个“闹钟/触发器”：条件满足时，
   再提交一张新的任务单。挂机队列因此由许多独立的 `TaskInstance` 组成。
4. 同一份 YAML 可以产生多张任务单；每张任务单在进入队列时读取并冻结自己的内容。之后
   GUI 修改文件，只影响下一张任务单。
5. 一次任务内部可以有业务必需的连续步骤（例如一张战斗地图的节点流程），但“再次
   执行同一任务”必须由触发器重新提交，不能由入口或 Processor 偷偷追加循环。

首期默认规则：同一触发器产生的任务已有一张处于运行/排队状态时，新的重复触发先忽略，
避免网络重试或轮询产生无限重复队列；确实需要每次都排队的业务再单独声明。

### 三、YAML 校验要像四道业务检查

后端必须把校验作为任务准入的硬门槛，GUI 可以提前提示，但不能替代后端校验：

1. **文件检查**：路径存在、确实是文件、位于允许的任务目录内，不能借软链接越界。
2. **格式检查**：YAML 能正常解析，顶层结构正确，包含版本和任务类型等必需元数据。
3. **字段检查**：该任务类型需要的字段齐全，类型和范围正确，拼写错误的未知字段拒绝。
4. **业务检查**：字段组合有意义，例如章节、地图、舰队和停止条件之间不能互相矛盾。

设备是否连接、当前页面是否正确、舰队是否暂时可用属于执行前/执行中的运行条件，不应
伪装成 YAML 格式错误。格式错误在排队前拒绝，不产生 `task_id`；运行条件失败则属于
已接受任务的执行失败，并保留清理结果。

### 四、兼容旧指令和旧 YAML 的最小方案

- `python`、`uv` 等只是启动脚本的方式；兼容层转换的是脚本已经解析出的参数和旧 API
  参数，不能接收任意 shell 字符串执行。
- 旧 CLI/API 只为明确承诺兼容的入口保留薄 facade：识别旧参数 → 生成统一任务单。
- 旧 YAML 建议通过一次性的迁移工具转换；切换完成后，Processor 只认一种新格式，不把
  新旧两套字段分支散落到各个 Executor。
- 为降低迁移量，新格式可以先只增加少量元数据（例如 `schema_version`、任务类型），
  保留现有任务字段布局；具体字段名和类型由各业务逐项确定，不预建巨型通用 YAML。

### 五、GUI 持续看到状态是什么意思

这里有三个不同概念，首期只需要前两个：

1. **任务记录持续存在**：Processor 在任务终态前持续保存任务单的状态、进度和错误；
   任务结束后保留结果摘要，供队列和历史显示。
2. **状态通知**：每次状态变化通过 WebSocket 推送；GUI 断线或漏消息时，用 HTTP 查询
   同一个 `task_id` 的权威快照补齐，不依赖“只收实时消息”。
3. **跨进程持久化**：后端重启后仍能恢复任务历史/队列。这需要磁盘数据库或文件，首期
   不强行引入；首期可将未完成任务标记为 `interrupted`，避免假装自动恢复。

### 六、需要提前定下的几个小规则

以下是业务上真正会影响 GUI 行为的细节，建议采用括号内默认值：

| 问题 | 建议默认 |
|---|---|
| YAML 无效时是否入队 | 不入队，直接返回具体校验错误。 |
| 系统未启动时提交任务 | 拒绝，不在路由内临时启动设备。 |
| GUI 请求超时后重试 | 使用 `client_request_id`，返回原任务，不重复执行。 |
| 排队任务取消 | 立即标记取消，不启动执行器。 |
| 运行任务取消 | 等最近安全节点、回到规定页面后标记取消。 |
| 任务异常 | 标记失败，保留根因；不能改写成取消。 |
| 定时重复触发 | 同类任务已有运行/排队实例时忽略；业务有需要再改。 |
| GUI 断线 | 任务继续运行；重连后按 `task_id` 查询快照。 |
| 后端重启 | 未完成任务标记 `interrupted`，首期不自动恢复。 |

这些默认规则不要求用户一次性设计代码，只需要在遇到具体业务例外时再调整。

### 七、用户确认后的最小业务模型

- 公开入口只有后端 CLI 和 GUI HTTP；两者经过指令识别/兼容转换后，直接交给 Processor。
- GUI 的任务来源是 YAML 路径；后端在准入时校验 YAML，读取并冻结一次，生成一张任务单。
- 后端最小执行边界是一次有限任务。重复执行由 GUI 或后端触发器再次提交任务，因此挂机
  队列由多张独立任务单组成，而不是一个永不结束的任务。
- `RuntimeHost`、`RuntimeControl`、`TaskCommand` 不是额外业务层的名称；对业务只解释为
  “系统启动开关”和“统一任务请求”。实现时优先复用现有模块，不为这些术语预建空壳框架。

## 2026-08-30：入口模型修订与宏观待决问题

以下内容覆盖本纪要中先前与用户最新决定冲突的提案。

### 一、执行次数改为入口参数

- YAML 不再保存 `times` 或同义的执行次数字段；现有 YAML 的业务字段布局继续保留，
  不为架构升级强制重写一套新格式。
- CLI 使用命令参数传递执行次数，GUI API 使用单独的执行次数参数传递；命名建议为
  `count` 或 `repeat_count`，不再把它混入 YAML。
- 一次请求的执行次数由 Processor 在准入后展开为 N 个一次性队列项。每个队列项仍然
  只有一次有限执行，不能让 Executor 内部形成无限循环。第一期不必新增父任务/批处理
  框架；若 GUI 需要聚合显示，再增加轻量关联编号。
- 高优先级插队时，当前队列项按暂停协议冻结，尚未执行的队列项保留在原队列中；恢复时
  继续当前项，再按原顺序执行剩余项。执行次数只在一个队列项到达终态后计数，暂停和
  恢复不会重复消耗次数。

以下两点仍需按业务决定：某个队列项失败后是否继续剩余项；用户停止时是只停止当前项，
还是停止同一次 `count` 请求产生的全部剩余项。

### 二、暂停、停止、中断的业务含义

三者不是同义词：

| 行为 | 设备连接 | 当前任务 | 后端系统 |
|---|---|---|---|
| 暂停 | 保留 | 保留进度和检查点，稍后恢复 | 继续运行并可执行插队任务 |
| 停止 | 保留 | 到安全节点、回规定页面后标记取消 | 继续运行并可接收新任务 |
| 中断 | 无条件关闭 | 不保证清理和终态，清空运行上下文 | 关闭后端运行连接/运行时 |

这里的“中断”按用户定义视为强制关闭路径：无论任务在哪个步骤，都不等待安全节点。
它与正常停止不同，不能保证 GUI 收到一个完整的取消结果。正常关闭 GUI 时，如果有
运行中任务，GUI 先提示用户二次确认；确认后究竟选择“等待安全停止”还是“立即中断”，
需要在 GUI 交互上明确区分，不能让一个模糊的“关闭”同时代表两种语义。

### 三、YAML 兼容策略修订

- 第一阶段沿用当前 YAML 字段，不强制添加 `schema_version`、`task_type` 或新的公共
  字段；一次性迁移工具以后可以作为外挂解决旧文件升级。
- 任务种类不能在没有依据时靠 Executor 猜测。若 GUI 只传 YAML 路径，则任务种类必须
  由 API 的任务入口、CLI 子命令或规范化目录得到；如果同一路径可能对应多个业务，
  就必须额外传一个很小的任务种类标识，否则后端无法可靠选择执行器。
- 旧 CLI/API 的公开行为默认保留，兼容层只负责旧参数 → 新任务请求的转换；这是架构
  重构而不是重制。未公开的内部导入和临时脚本不作为长期契约，需另列兼容清单。

### 四、优先级由两边共同遵循

- GUI 可以按照同一张优先级规则表进行队列展示、插队编排和用户提示；这样用户看到的
  顺序与实际意图一致。
- Processor 仍是最终裁决者：它重新检查优先级、抢占条件和安全节点，防止 GUI 与后端
  版本不一致。GUI 不是任意填写优先级，而是使用统一业务规则选择插队位置。
- 当前本地单机部署不单独引入请求幂等键；GUI 负责禁用重复提交/重复点击。将来出现
  远程部署或可复现的重复请求，再增加幂等字段和状态。

### 五、系统与 CLI 的生命周期

- GUI 正常关闭时，默认先检查任务是否运行；运行中必须二次确认。GUI 被强制终止时，
  后端按“中断”语义关闭运行时并清空上下文，不自动恢复任务。
- 这一保证依赖 GUI 与后端的部署关系：若 GUI 始终作为后端子进程的拥有者，可以用
  进程生命周期实现强制关闭；若后端被独立启动，单靠 HTTP 无法可靠知道 GUI 已崩溃，
  就必须另加心跳或进程监督。首期建议明确采用前一种本地部署关系，不预建心跳系统。
- CLI 的交互式实时状态显示记录为后续 TODO。当前 CLI 只需要提交任务并按需要等待/退出，
  不为此提前引入终端渲染框架。

### 六、还需用户决定的宏观业务问题

1. **任务种类来源**：GUI API 是否按业务分入口（例如演习接口带 YAML 路径），还是所有
   业务共用一个接口并额外携带 `task_type`；仅凭路径自动推断是否可接受？
2. **重复执行的显示方式**：`count=3` 后 GUI 是否显示 3 个独立队列项，还是只显示一个
   聚合项并展开查看？
3. **重复执行的停止范围**：停止当前项，还是连同本次 `count` 产生的剩余项一起取消？
4. **重复执行的失败策略**：某一项失败后继续后续项，还是立即停止剩余项？
5. **队列权威来源**：GUI 只是提交/取消/插队请求并显示 Processor 队列，还是 GUI 维护
   一份完整队列再逐项发送？建议后端 Processor 持有真实队列，GUI 只做编排意图和显示。
6. **正常关闭确认**：确认关闭时默认优雅停止并回主页，还是允许用户选择直接中断？
7. **强制关闭范围**：“关闭后端连接”是否意味着结束后端进程，还是只断开模拟器并
   销毁运行时；两者对部署和下次启动不同。
8. **CLI 等待语义**：CLI 提交后默认等待整批完成，还是立即返回任务编号；实时状态显示
   可在后续 TODO 中补上。
9. **兼容清单**：哪些现有 CLI、GUI API、Python 公开函数必须在 Sakuya 第一阶段继续可用；
   默认按“现有 GUI API + 文档中的公开 CLI/API 全部保留”处理。
10. **GUI 关闭后的定时器**：由于后端随 GUI 关闭，GUI 持有的定时任务是否一并停止；若
    需要后台继续挂机，则必须由独立 CLI/后端进程持有触发器。

## 2026-08-30：入口修订后的宏观待决问题（按优先级）

以下问题不是新增技术层，而是必须先确定的用户可见业务规则。前文与本节冲突时，以本节
和用户后续确认的规则为准。

### 阻塞 Processor 落地的四个问题

1. **`count` 的显示方式**

   CLI/API 传入 `count=N` 后，后端可以在内部展开 N 个一次性执行项，也可以对 GUI 只
   展示一个“批次”并在内部循环。两者都能暂停和恢复，但取消、失败和进度显示不同：

   - 方案 A：返回 N 个执行项/任务编号，GUI 看到 N 行；
   - 方案 B：返回一个批次编号，GUI 看到一行，显示 `完成 x/N`。

   建议内部按方案 A 保持一次性边界，GUI 是否聚合显示可以另定；但必须先决定接口返回
   一个编号还是一组编号。

2. **任务类型从哪里来**

   既然暂时不改现有 YAML、GUI 又主要传路径，后端仍需要可靠知道“这是普通出征、演习、
   远征还是维修”。可选方式只有：

   - 不同业务使用不同 API 入口（例如演习入口天然带类型）；
   - API 额外传一个任务类型；
   - 由旧目录/文件命名推断。

   建议使用前两种之一，目录推断只作为旧兼容入口；不能让执行器凭字段猜测业务。

3. **批次中的失败和停止范围**

   `count=5` 时，如果第 2 次失败，是否继续第 3~5 次；用户点击停止时，是停止当前
   一次并保留剩余次数，还是整批都停止。这个决定会直接影响 GUI 进度和 Processor 的
   状态，不宜留给实现者自行猜测。

4. **GUI 队列与 Processor 队列谁说了算**

   GUI 可以按优先级编排和展示队列，但真正操作模拟器的顺序必须只有一个权威。建议 GUI
   提交“新增/插队/取消”意图，Processor 返回实际队列；GUI 不把整份本地队列覆盖回后端。
   否则 GUI 和后端同时改队列时会出现顺序漂移。

### 可以随后决定的三个问题

5. **强制关闭如何被发现**

   若 GUI 与后端是两个独立进程，GUI 被任务管理器强制结束时，后端不会从 HTTP 自动得知。
   要满足“立即关闭后端并清空上下文”，部署关系必须明确为 GUI 持有/监管后端子进程，或
   以后增加心跳监督。首期最简单的是前者；正常关闭仍由 GUI 先二次确认。

6. **正常停止后的队列处理**

   正常停止与强制中断不同。正常停止系统时，当前任务是优雅取消；尚未开始的任务是
   全部取消、保留到下次启动，还是交给 GUI 再次提交，需要固定一个规则。建议全部取消，
   因为本地运行时关闭后不保留任务上下文。

7. **启动时的未知页面**

   强制中断可能把游戏留在任意页面。下次启动必须先执行一次“状态确认并回到首页”，
   成功后才允许接收任务；不能直接拿旧的任务进度继续点击。这个是启动流程的业务门槛，
   不是某个 Executor 自己补的异常分支。

### 不影响当前架构、但需要记账的规则

8. 一次任务的“执行一次”按业务用例解释：例如一次出征可包含地图节点和结算步骤，
   `count` 重复的是完整出征，不是其中每个点击或节点。
9. YAML 在提交时读取并冻结；GUI 正在保存文件时提交若读取不完整，应拒绝本次任务，
   不使用半份内容。
10. 任务终态记录至少保留到 GUI 能看到结果并刷新队列；更长的历史保留和磁盘持久化后置。
11. 旧 CLI/API 的行为继续保留，内部实现可以换成适配器；“兼容”指行为和公开调用方式，
    不指内部模块路径永远不变。
12. CLI 的交互式状态显示继续作为 TODO；当前 CLI 只需能提交、等待（若选择等待）和
    显示终态。
